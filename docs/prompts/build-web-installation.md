<context>
学園祭の展示「あなた色写真展」を、仕様書 `docs/README.md` に従ってWebインスタレーションとして実装する。仕様書が要件の正本で、技術スタック、状態遷移、通信、受け入れ条件はすべてそこに定義されている。作業を始める前に全文を読み、以降も判断に迷ったら仕様書の該当節へ戻ること。

仕様書が決めていないのは、展示ディスプレイとiPadの演出の見た目である。この部分を抽象的なグラフィックスで表現してほしい。
</context>

<design_direction>
展示の主役は写真作品と、来場者に選ばれた「色」そのものである。グラフィックスは、写真を見る前後の時間に色の体験を深める役割を持つ。

色面、円・帯・弧などの単純な幾何形態、グラデーション、呼吸のようにゆっくりした動きだけで画面を構成する。具体的な物、人、風景、文字記号を描かない。色は仕様書の結果色定義から取り、一つの画面では少数の色面を大きく使う。動きは、来場者が教室の中を歩きながら視界の端で変化に気づく程度の速さにする。展示ディスプレイは鑑賞のための画面なので、ゲームのような速い反応にはしない。

次の表現は、画面がスクリーンセーバーや汎用の「AIが作った背景」に見えてしまい、写真作品と競合するため使わない。発光するパーティクルの群れ、ネオンのグロー、すりガラス風のぼかしパネル、画面全体を流れ続けるメッシュグラデーション、ランダムに漂う小さな点、紫から青への定番グラデーション。最初の実装を見て別の定番表現に寄っていたら、それもこの一覧に加えて作り直す。

演出を設計するうえで、仕様書から導いた前提が三つある。

- 展示ディスプレイには回答内容が届かない（8.5節）。質問中の「回答に反応する演出」は、`revision` の増加を「一問確定した」合図として使う。どの色に近づいているかを推測できる見せ方は、結果発表の驚きを損なうので避ける。
- 複数のディスプレイが一つの作品として見えるように、動きは補正済みサーバー時刻と `sessionId` から決定的に計算し、画面ごとの違いは `displayOrder` から作る。こうすると再接続した画面も、ほかの画面と同じ位置から再開できる。
- 結果の切り替え時刻は同期計測の基準になる（8.7節）。結果側の演出は、切り替えた後に始まるように組む。

`prefers-reduced-motion: reduce` の環境でも、色面の切り替えと静止した構図だけで各状態が伝わるようにする。照明について仕様書11章が避けている強い高速点滅は、画面の演出でも同じ理由で使わない。
</design_direction>

<instructions>
1. 実装の前に `docs/visual-language.md` を書き、状態ごとの構図、形、動きの速さ、8色それぞれの見せ方、reduced-motion時の代替を決める。演出の実装はこの文書に従う。
2. 仕様書のMVPを実装する。範囲は仕様書が定めたものだけとし、仕様書にない機能、設定項目、抽象化は追加しない。
3. 仕様書16章の要決定事項は、仕様書の仮値と「仮」と分かるデータで埋める。仮データに合わせて検証を緩めたり、テスト用の値を実装へ直接書き込んだりはしない。
4. 演出は、ブラウザで展示ディスプレイを複数開いて実際に確かめる。iPad画面から一回の診断を最後まで進め、各状態のスクリーンショットを撮って `docs/visual-language.md` と見比べ、ずれていれば直す。

作業は長くなるので、`docs/progress.md` に完了したこと、次にやること、判断に迷った点を随時書く。コンテキストが切り替わったら、この記録と `git log` から再開する。意味のある単位で区切ってコミットする。

ユーザーの判断がないと進めない点があっても、そこで作業を止めない。`docs/progress.md` に記録し、その判断に依存しない部分を先に進める。
</instructions>
