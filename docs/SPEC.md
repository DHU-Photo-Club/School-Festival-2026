# あなた色写真展 - 診断インタラクティブ展示 - 仕様書

## 1. 文書の位置づけ

本書は、学園祭で一度だけ実施するあなた色診断展示の企画・制作・当日運用における基準とする。
未確定事項は16章「要決定事項」に集約し、それ以外はMVPの暫定仕様として実装を進める。

一回きりの学内展示なので、当日に止まらず、止まってもスタッフがすぐ戻せることを優先する。公開サービス向けの冗長な仕組み（再送、冪等性、端末認証、計測の記録など）は持たない。

## 2. 体験の目的

来場者が直感的な質問に答えると、AIが回答全体を読み取って「今のあなた」を表す二色と一つの色名を提案し、写真・画面・教室内の光がその色へ変化する体験を提供する。
この診断は、展示作品として楽しむためのものとし、心理検査の精度や人物の分類を目的としない。「似合う色」の断定ではなく、「回答から選んだ今回の色の表現」と表現する。

質問、AIによる色と写真の選定の正本は`refs/handoff/実装仕様書.md`（版1.0、以下「handoff」）とする。本書はそれを展示の構成へ組み込む方法を定める。

### 体験完了の条件

- 来場者が説明を受けなくても、開始から結果表示まで一人で操作できる。
- 結果の二色、色名、回答の読み取りが同時に表示される。
- 結果表示に合わせて、すべての展示ディスプレイが同じ結果へ切り替わる。
- 次の来場者が前の回答を見ずに、新しい診断を開始できる。

## 3. MVPの範囲

### 実施するもの

- iPad上での診断操作
- 回答全体からのAIによる二色と色名の選定（6章）
- 複数ディスプレイへの同期表示
- 二色と回答に合う写真作品の選定と表示
- 結果画面からのデジタル結果受け渡し
- スタッフによる強制リセットと接続状態の確認
- Matter対応のスマート電球を、通常は白色、結果の表示中は二色にする照明連携（11章）
- 会場のスピーカーから流すBGM、ガラス音、ナレーション、回答と完了の効果音（11.2節）

### MVPでは実施しないもの

- 氏名、年齢、連絡先などの個人情報収集（`intro`で入力するニックネームは来場者が自由に決める呼び名で、本名を求めない）
- カメラや顔画像を用いた自動診断
- 来場者自身による写真投稿
- AIによる画像の生成（AIはパレットの色、色名、説明文、写真の内容の判定だけを担う）
- フルカラー印刷
- 複数人の同時診断

即時印刷と、電球の色を変える以外の照明制御は、機材と現地検証の結果を踏まえて追加する。

## 4. 利用者と端末

| 種別             | 役割                     | 開くURL                          |
| ---------------- | ------------------------ | -------------------------------- |
| 来場者           | 診断を受ける             | iPadで回答し、QRで結果を受け取る |
| 診断用iPad       | 診断を操作する           | `/`                              |
| 展示ディスプレイ | 破片の群れと結果の色を表示する | `/display/1`、`/display/2`…      |
| 写真用           | 写真だけを巡回表示する   | `/photo/1`、`/photo/2`…          |
| 電球の中継       | スマート電球の色を変える | 会場のPCで`pnpm lights`を動かす  |
| サウンド         | 会場のスピーカーから音を出す | 会場のPCのChromeで`/sound`を一つだけ開く |
| 運営スタッフ     | 当日の進行と復旧を行う   | `/admin`                         |
| 結果ページ       | 来場者の端末で結果を開く | `/result/{結果ID}`               |

iPadの画面ミラーリングは使用しない。各端末がそれぞれのURLを開き、同じ展示状態を共有する。

展示ディスプレイの番号は、来場者から見た順に1から振る。番号は二色の割り当てと演出のずれ（7.2節）に使う。同じ番号を二台で開かない。

本番のブラウザは、iPadが最新版Safari、展示ディスプレイ、写真用、管理画面がChromeの最新安定版とする。

## 5. 一回の体験フロー

目標所要時間は一人あたり2分以内、うち質問回答は60秒以内とする。

| 状態       | 段階               | iPad                                                  | 展示ディスプレイ                                 | 終了条件                                       |
| ---------- | ------------------ | ----------------------------------------------------- | ------------------------------------------------ | ---------------------------------------------- |
| `idle`     | 待機               | 歓迎文言と「はじめる」を表示                          | 全作品を静かに巡回表示                           | 「はじめる」を押す                             |
| `sequence` | 演出               | シーケンスのコンポーネントを表示                      | 待機の破片の上にシーケンスのコンポーネントを重ねる | 再生時間が過ぎると、サーバーが次の段階へ進める |
| `intro`    | 導入               | 進捗バーとニックネームの入力欄を表示                  | 待機表示を継続                                   | ニックネームを入力して「→」を押す              |
| `question` | 質問               | 一問ずつ質問文と、入力方式（6.1節）に応じた入力を表示 | 灰色の破片の輪を表示（回答には反応しない）      | 全問に回答する                                 |
| `judging`  | 判定               | 判定演出を表示（最短10秒、AIの選定が終わるまで）       | 全画面を一度暗くし、画面の外から中心へ集まる細かい塵を見せて、結果演出に備える             | AIの選定が終われば`result`、失敗なら最終問へ   |
| `result`   | 結果発表・持ち帰り | 色名、二色、読み取り、QRコード、「最初に戻る」を表示  | 二色と選定した写真を一斉に表示                   | 「最初に戻る」または60秒経過で`idle`へ戻る     |

`sequence`は、iPadと展示ディスプレイで演出を再生し、再生時間が過ぎると自動で次の段階へ進む段階である。`src/data/sequences.ts`にはID、どの段階の直前に再生するか（`before`）、再生時間（`durationMs`）だけを定義し、見た目は`src/client/sequences/<id>/`のSvelteコンポーネント（iPad用の`Controller.svelte`と展示ディスプレイ用の`Display.svelte`）で自由に書く。`intro`と`question`のそれぞれについて、その段階へ入る直前に一つまで再生できる。仮データでは「はじめる」の後、`intro`の前に再生する。再生中はiPadに操作手段を置かない。

「持ち帰り」は独立した状態ではなく、`result`画面でQRコードを読み取る行為を指す。

質問中は入力を操作して回答を選び、「次へ」で確定する。確定前の値はiPadの中だけで保持し、サーバーへ送らない。「次へ」を押してからサーバーの新しい状態が届くまで、入力と「次へ」を無効にして二重入力を防ぐ。前の質問へ戻った場合は既存回答を表示し、変更して再確定できる。

## 6. 診断仕様

### 6.1 質問

質問はhandoff 3章の5問とする（`src/data/questions.ts`、版`questions-v0.3`）。質問ID（`Q1`〜`Q5`）と選択肢ID（`q1_1`など）はhandoffの`config/questions.json`と同じにし、表示順を変えても維持する。Q1、Q3、Q5は合意済み、Q2とQ4はhandoffの現行案で、最終確定ではない。

| 質問 | `kind`     | 入力方式     | 選び方                                                            |
| ---- | ---------- | ------------ | ----------------------------------------------------------------- |
| Q1   | `multiple` | 複数選択     | 7択から1〜2つ。「今は、どれとも決められない」（`q1_7`）は単独選択 |
| Q2   | `multiple` | 複数選択     | 5択から1〜2つ                                                     |
| Q3   | `slider`   | スライダー   | 「まず、じっくり知りたい」―「まず、試してみたい」の間の位置       |
| Q4   | `map`      | 2Dマップ     | 左右が内向き―外向き、上下がエネルギーが高い―低い の平面上の位置   |
| Q5   | `ranked`   | 順位つき選択 | 5択からちょうど2つを、1位、2位の順に選ぶ                          |

入力方式は次の5種類とする。単選択は今の5問では使わないが、入力方式として残す。

| `kind`     | 入力方式     | 回答                                           |
| ---------- | ------------ | ---------------------------------------------- |
| `single`   | 単選択       | 選択肢ID                                       |
| `multiple` | 複数選択     | 選択肢IDの配列（選択肢の定義順）               |
| `ranked`   | 順位つき選択 | 選択肢IDの配列（選んだ順。先頭が1位）          |
| `slider`   | スライダー   | 左端0から右端1までの位置                       |
| `map`      | 2Dマップ     | `{ x, y }`（xは左端0〜右端1、yは上端0〜下端1） |

- 各問に案内文（`guide`、例:「直感で、最大2つ選んでください。」）を持たせ、質問文の下に表示する。
- 複数選択と順位つき選択は、選択済みの選択肢を押すと外す。上限まで選んでいると、選んでいない選択肢は押せない。順位つき選択で1位を外すと、2位が1位へ繰り上がる。
- 単独選択の選択肢（`exclusive`）を押すと、ほかの選択をすべて外してそれだけにする。単独選択の選択肢を選んでいる間にほかの選択肢を押すと、単独選択の選択肢を外す。上限まで選んでいても、単独選択の選択肢へは切り替えられる。単独選択は複数選択の質問でだけ使える。
- スライダーと2Dマップは真ん中から始め、そのまま「次へ」で送れる（handoffの案内文「真ん中でも大丈夫です」）。AIへの指示では、真ん中の50は初期値でもあるため強い根拠にしないとしている。
- スライダーは等間隔に5段階の回答位置（`far-left | left | center | right | far-right`）を置き、2Dマップは平面を3×3の区画（`top-left`〜`bottom-right`）に分ける。回答位置と区画は画面の補助文だけに使い、回答は位置そのものとする。スライダーの補助ラベル（`interpretation`、例: 0〜39は「理解から入る傾向」）はAIへの入力に添える。
- スライダーのつまみと2Dマップのピンはスナップせず、指を離した位置に止まる。iPadは位置を小数第3位に丸めて送る。選んでも自動では次へ進まず、「次へ」を押した時点で選んでいる回答を送る。
- 選択式の質問は、新しく開いた時点では未回答とし、選択数が下限に届くまで「次へ」を無効にする。
- 正解・不正解や得点表示は行わない。画面上部に現在の質問番号を表示する。
- サーバーは、表示中の質問の入力方式に合わない回答（未定義のID、範囲外の選択数、重複、複数選択で定義順でない並び、単独選択とほかの選択肢の組み合わせ）を拒否する。質問定義を変えてデプロイした後は、変更前に保存した回答のうち定義に合わないものを除く。最終問に回答した時点で未回答の質問が残っていれば、選定せずにその質問へ戻す。

### 6.2 風景色パレット

色はhandoff 4章の13色パレット（版`scenery-v2`、`src/data/palette.ts`）から選ぶ。写真から抽出した色ではなく、自然や都市風景の写真につながる展示用の候補色である。写真の収集後に見直す場合は版を変える。

| ID          | 色名               | HSL         | 風景の例                   |
| ----------- | ------------------ | ----------- | -------------------------- |
| `vermilion` | 朱色               | 12, 76, 53  | 紅葉、鳥居、赤い外壁       |
| `orange`    | 夕映えオレンジ     | 28, 79, 57  | 夕日、柑橘、街の灯り       |
| `amber`     | 琥珀色             | 38, 78, 54  | 夕方の光、黄葉、灯り       |
| `gold`      | 山吹色             | 45, 83, 55  | 黄色い花、銀杏、日差し     |
| `leaf`      | 若葉色             | 85, 55, 48  | 新緑、日を受けた草木       |
| `forest`    | 深緑               | 128, 48, 39 | 森、木陰の葉               |
| `emerald`   | エメラルドグリーン | 147, 58, 43 | 光を受けた緑、水辺         |
| `jade`      | 翡翠色             | 160, 44, 46 | 緑がかった水面、葉の影     |
| `sky`       | 空色               | 207, 66, 61 | 晴れた空、遠景             |
| `blue`      | 瑠璃色             | 218, 65, 51 | 青空、海、青い建物         |
| `indigo`    | 藍色               | 232, 52, 47 | 薄暮、青い影、染められた布 |
| `wisteria`  | 藤紫               | 269, 37, 59 | 藤の花、夕暮れの雲         |
| `rose`      | 薔薇色             | 347, 57, 61 | 花びら、夕焼けの雲         |

- 色値はパレット側で管理し、AIには自由なHSL値を出させない。HSLから8bitのsRGBへの変換はhandoffの`reference-simulator/palette.mjs`と同じ式にする（`src/shared/palette.ts`）。
- 結果表示の背景色は色相を保って暗くした色（`hsl(h, min(s, 60), 14)`）、文字色は明るい色（`hsl(h, 40, 92)`）としてパレットから作る。両者のコントラスト比は4.5:1以上とし、満たさない色はproduction buildを失敗させる。
- 二色の混色プレビューは、8bit sRGBの各成分を直線補間した13段のグラデーションとする（handoff 6章）。

### 6.3 AIによる二色と色名の選定

最終問の回答を受理すると、会場サーバーが回答全体をAIへ渡し、パレットから異なる二色と、二色全体を表す一つの色名を選ばせる（handoff 2章、5章）。実装は`src/server/ai/`。質問ごとに色を固定する計算や、配点による判定は行わない。

1. **色の選定**: 指示（`prompts.ts`の`COLOR_SELECTION_PROMPT`、handoffの`prompts/color-selection.txt`の原文）、パレット、回答データを送る。回答データには質問文、回答の文言、スライダーと2Dマップの軸の語と0〜100の値を含め（handoffの`examples/color-ai-input.json`の形、`input.ts`）、ニックネームは含めない。2Dマップの縦軸は、画面の下端（エネルギーが低い）を0、上端を100として渡す。
2. **出力の検証**（`color.ts`）: JSONの形、必須項目、文字数（色名24字、命名理由100字、読み取り150字、各色の理由100字、関係150字）、色が2件で異なること、パレットにあるID、パレットの版、根拠の質問IDが有効なこと、自由なh/s/lがないことを確かめる。色名に二色の列挙の記号（`×`、`＋`、`+`、`/`、`／`）や改行があれば使わない。
3. **写真の選定**: 確定した二色、回答データ、写真カタログ（内容のタグ、雰囲気のタグ、説明）を送り、内容が合う写真を判定させる（`prompts.ts`の`PHOTO_SELECTION_PROMPT`）。色の適合はAIに判定させず、写真の色タグから実装側で判定する（handoff 7.1節の「人のタグ」の方式）。カタログにない写真ID、重複、根拠の欠けた項目は捨てる。
4. **写真の組み立て**（`src/shared/photo-selection.ts`）: 段階1（色と内容の両方が合う）→段階2（色だけ合う）→段階3（内容だけ合う）の順に、`PHOTO_POLICY.sessionPhotoCount`枚（仮に10枚）まで選ぶ。各写真は上位の一つの段階だけに属し、同じ写真を二度選ばない。足りない枚数は記録し、架空の写真や重複で埋めない。段階内の順位はhandoffで未決定のため、段階1と段階3はAIの判定順、段階2は全体の色タグで合う写真を一部分の色タグで合う写真より先にする。

失敗時の扱い:

- 一回の呼び出しは9秒で打ち切る。送信の失敗、HTTPエラー、時間切れ、検証に通らない出力は、それぞれ一度だけやり直す（`src/data/ai.ts`の`AI_SETTINGS`）。
- 色の選定がやり直しても失敗したら、結果を作らずに最終問へ戻す。回答は保ち、iPadに「色をうまく選べませんでした。もう一度「次へ」を押してください」と表示する。固定の計算で代わりの結果を作らない。
- 写真の選定が失敗したら、二色は変えずに色の適合だけで写真を選ぶ（内容は根拠不足として段階2まで）。
- 選定全体の上限は30秒とし、それまでに決まらなければ最終問へ戻す。

AIの接続は`MISTRAL_API_KEY`で有効にする（14章）。開発とE2Eテストでは、AIへ接続せずに決まった二色を返す仮の選定（`AI_STUB=1`）を使える。どちらも設定しなければ結果を決められないため、最終問を答えるたびに最終問へ戻る。

### 6.4 結果の記録

一回の体験の結果は、結果ページのIDを付けた記録（`ResultRecord`、`src/shared/result.ts`、版`color-result-v1`）として会場サーバーのSQLiteに保存する。後から再生成せずに振り返れるよう、次を含める（handoff 8章）。

- 結果ID、作成時刻、質問定義とパレットの版、モデル名
- 全問の回答
- 色の出力（色名、命名理由、読み取り、二色と各色の理由・根拠の質問ID、関係）
- 写真の選定（各写真の段階、色の根拠、内容の根拠、要求枚数、不足枚数、内容判定の状態）

結果IDは推測されにくい16桁の16進数（8バイトの乱数）とする。展示状態には、表示に使う色名、読み取り、二色、写真IDと結果IDだけを置く。

## 7. 画面仕様

### 7.1 iPad操作画面

- 縦向きを基本とし、横向きでも操作不能にならないレイアウトにする。
- 一画面に一つの主操作だけを置く。
- スライダーは画面全体を縦の仕切り線で左右に分け、広い側の語を選んでいるとみなす（回答が左の語に近いほど仕切り線は右へ寄る）。画面の任意の位置のタップとドラッグの両方で、指の位置へ仕切り線を動かせるようにする。ただし、押し間違いで回答が変わらないよう、下部のボタン列は操作面から除く。つまみは直径40px以上とする。読み上げとキーボード操作のために、5段階の回答位置を見えないラジオボタンとしても置き、矢印キーで別の回答位置へ移ると仕切り線がその回答位置へ動くようにする。
- スライダーは広い側の語を大きく、狭い側の語を小さく表示する。最も近い回答位置の補助文を質問文の直下へ表示する。
- 2Dマップの平面は一辺220px以上の正方形とし、平面上の任意の位置のタップとピンのドラッグの両方で、指の位置を選べるようにする。9区画の中心に印を常時表示し、ピンを含む区画の印を拡大する。その区画の補助文を平面の下へ表示する。読み上げとキーボード操作のために、9区画を見えないラジオボタンとしても置き、矢印キーで別の区画へ移るとピンがその区画の中心へ動くようにする。
- 質問文の下に案内文を表示する。
- 選択肢は高さ64px以上のボタンとし、単選択は丸、複数選択と順位つき選択は四角の印を左に置く。選んだ選択肢は塗りつぶし、印に単選択は点、複数選択はチェック、順位つき選択は順位の数字を入れる。単独選択の選択肢は、ほかの選択肢と区別できるよう一行全体に置く。
- 未回答、操作中、確定待ち、確定済み、無効の状態を、つまみ・ピン・選択肢の形、枠、ラベルで見分けられるようにする。色だけで状態を区別しない。
- AIの選定に失敗して最終問へ戻ったときは、質問文の下に「色をうまく選べませんでした。もう一度「次へ」を押してください」を表示する。次の操作で消す。
- 結果画面には色名、二色の混色プレビュー（6.2節）、二色の色名、回答の読み取り、QRコードと結果URL（10.3節）、「最初に戻る」を表示する。背景と文字には一色目の背景色と文字色を使う。
- 通信が切れている間は「再接続しています」を全面に表示して操作を止める。再接続したらサーバーの状態をそのまま表示する。ブラウザを再読み込みしても、進行中の診断や結果へ戻る。

### 7.2 展示ディスプレイ

#### 7.2.1 画面番号

展示ディスプレイは`/display/{番号}`を開く。番号から1を引いた値を`displayOrder`とし、二色の割り当てと演出のずれに使う。台数を事前に登録する一覧は持たない。

#### 7.2.2 共通レイアウト

- 展示ディスプレイには写真を置かない。どの状態でも、背景面の上に三角形の破片の群れを描く（`docs/visual-language.md`）。写真は写真用の端末（7.3節）と結果ページだけで見せる。
- 待機状態の背景は`#0B0B0B`とする。結果状態では、その画面が見せる色（7.2.4節）の背景色を使う。
- 色名などの文字には、その画面が見せる色の文字色を使う。

演出の見た目は `docs/visual-language.md` に従う。

#### 7.2.3 待機表示

背景`#0B0B0B`の上に、灰色の破片の輪を、半径だけ小さく縮めて描く（質問中の輪の半径の0.3倍。破片の大きさは変えない）。破片の枚数も質問中の0.3倍に減らす。輪の動きは質問中（`question`）と同じ。待機中に写真や展示タイトルは表示しない。`intro`の直前に再生するシーケンスから`intro`の間は、破片が3秒でパレットの全色に色づきながら、輪の内側を空けたまま画面いっぱいに散らばり、破片の大きさが質問中の2倍、枚数が全枚数になり、画面の中央に「あなた色写真展へようこそ」を`#E8E6E3`で表示する。文字は、直前のシーケンスがあればその開始から、なければ`intro`の開始から3秒でゆっくり現れ、シーケンスから`intro`へ移っても途切れない。現れ終えてから3秒見せたあと、「ようこそ」は1.5秒で消え、続けて説明の文「あなた色写真展は／あなたの気分や感性によって／変化する写真展です」（三行）が同じ位置に3秒でゆっくり現れ、質問へ移るまで見せる。質問へ移ると、破片は3秒で灰色の質問中の輪へ戻り、文字は1.5秒で消える。シーケンスのコンポーネントの上に重ねる。

#### 7.2.4 結果表示と割り当て

二色は画面の順に交互に割り当て、`displayOrder`が偶数の画面は一色目、奇数の画面は二色目を見せる。各画面は、その画面の色の背景色を全面に表示し、その中央へ文字色でパレットの色名を表示する。破片の群れは結果でも消えず、結果の二色で色づいたまま動き続ける。

結果の切り替え時刻は`judging`の`phaseEndsAt`とし、各画面が補正済みサーバー時刻でその時刻を待って切り替える。`result`開始後に接続した画面は結果演出を再生せず、完了状態をすぐに表示する。

### 7.3 写真用

写真用の画面は`/photo/{番号}`を開き、診断の状態とは関係なく、待機用プレイリストを8秒ごとに巡回表示する。番号ごとに開始位置を一作品ずつずらす。管理画面の端末一覧に表示するため、サーバーへは接続する。

### 7.4 管理画面

管理画面は`/admin`を開く。次を提供する。

- 現在の段階、結果の色名と二色（選定に失敗したときは「選定に失敗」）、セッションID。回答内容は表示しない。
- 診断受付の停止と再開。停止は新規開始だけを拒否し、進行中の診断は最後まで続ける。
- 全端末を待機状態へ戻す強制リセット。
- パレットの13色の表示確認（待機中だけ）。全画面にその色の背景と色名を表示する。
- 接続中の端末一覧と最終受信時刻。端末は診断用iPad、展示ディスプレイ、写真用、電球の中継、サウンドの5種別に分けて表示する。サウンドには再生状態（再生中、クリック待ち、読み込み中、一部の音源なし）も表示する。接続が切れたまま最後の受信から15秒を過ぎた端末は「切断」と表示する。タブを閉じるなどで接続を正常に閉じた端末は一覧から消える。

## 8. 同期と状態管理

会場サーバーが展示全体で一つの展示状態を持ち、保存して全端末へ配信する。

```text
sessionId: string | null
phase: idle | sequence | intro | question | judging | result
nickname: string | null
sequenceId: string | null
questionIndex: number | null
answers: Record<QuestionId, Answer>  // 単選択の選択肢ID、複数選択と順位つき選択の選択肢IDの配列、スライダーの位置（0〜1）、2Dマップの位置 { x, y }
result: { id, name, reading, colors: [PaletteId, PaletteId], photoIds } | null
judgeFailed: boolean
previewColorId: PaletteId | null
phaseStartedAt: number
phaseEndsAt: number | null
answeredAt: number | null  // 直前に質問の回答を受け付けた時刻。展示ディスプレイの波紋の起点
revision: number
accepting: boolean
```

時刻はサーバー時刻のUnix time milliseconds、`questionIndex`は0始まりとする。`nickname`は`intro`で入力したニックネームで、`idle`へ戻るまで保持する。`revision`は状態が変わるたびに1増える番号である。`answeredAt`は、質問への回答（最終問を含む）を受け付けた時刻で、「戻る」では変わらず、`idle`へ戻ると`null`になる。展示ディスプレイは回答の内容に反応せず、`revision`を描画に使わない。`answeredAt`だけを使い、その時刻から輪を縮め、縮み切って戻り始める瞬間（0.45秒後）に画面の中心へ波紋を広げる（`docs/visual-language.md`の3.2節）。`result`は6.3節の選定の結果で、`id`は結果ページのID。`judgeFailed`は直前の選定に失敗して最終問へ戻ったことを表す。

以前の版（8色の配点判定）で保存した状態（`judgeFailed`がない）を読んだときは、セッションを捨てて`idle`から始める。`accepting`は引き継ぐ。

### 8.1 初期値

保存した展示状態がないとき（会場サーバーの初回起動時）は、`phase`を`idle`、`accepting`を`true`、`revision`を0、`answeredAt`を`null`、`phaseStartedAt`を作成時刻とし、それ以外を空（`null`または`{}`）にする。

`idle`から開始するときに`crypto.randomUUID()`で新しい`sessionId`を発行し、`idle`へ戻るときに`null`へ戻す。

### 8.2 状態遷移と期限

| 現在の状態              | 契機                                      | 次の状態                          | 同時に行う処理                                                                                                 |
| ----------------------- | ----------------------------------------- | --------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `idle`                  | iPadの開始操作                            | `sequence`または`intro`           | 新しい`sessionId`を発行する。`intro`の前のシーケンスがあれば`sequence`へ入る                                   |
| `intro`                 | iPadのニックネーム送信                    | `sequence`または`question`        | ニックネームを保存する。`question`の前のシーケンスがあれば`sequence`へ入り、なければ`questionIndex`を0にする   |
| `sequence`              | 再生時間が経過                            | `intro`、`question`、または`idle` | シーケンスの`before`の段階へ入る（`question`なら`questionIndex`を0にする）。定義が見つからなければ`idle`へ戻す |
| `question`              | 最終問以外の回答                          | `question`                        | 回答を保存し、`questionIndex`を1進める                                                                         |
| `question`              | 「戻る」                                  | `question`                        | `questionIndex`を1戻し、既存回答は保持する                                                                     |
| `question`              | 最終問の回答                              | `judging`                         | 回答と`questionIndex`を保ったまま、AIの選定（6.3節）を始める。`phaseEndsAt`は30秒後                            |
| `judging`               | AIの選定の成功                            | `judging`                         | 結果を記録として保存し、`result`を設定して`answers`を消去する。`phaseEndsAt`を早める                           |
| `judging`               | AIの選定の失敗                            | `question`                        | 最終問へ戻し、`judgeFailed`を`true`にする。回答は保つ                                                          |
| `judging`               | `phaseEndsAt`（結果あり）                 | `result`                          | 60秒後を`phaseEndsAt`にする                                                                                    |
| `judging`               | `phaseEndsAt`（結果なし、選定の時間切れ） | `question`                        | 最終問へ戻し、`judgeFailed`を`true`にする                                                                      |
| `result`                | 「最初に戻る」または60秒経過              | `idle`                            | セッション状態を初期化する                                                                                     |
| `intro`または`question` | 最終操作から5分経過                       | `idle`                            | 放置された回答とセッションを消去する                                                                           |
| 任意                    | 管理画面の強制リセット                    | `idle`                            | 現在の処理を中止してセッション状態を初期化する                                                                 |

`phaseEndsAt`は`sequence`では再生時間後、`judging`では30秒後（選定が早く終われば、開始から2秒後と現在から0.8秒後の遅いほうへ早める。全画面は新しい`phaseEndsAt`で同時に結果へ切り替わる）、`result`では60秒後、`intro`と`question`では最後のiPad操作から5分後、`idle`では`null`とする。期限は会場サーバーのタイマーで処理する。タイマーが遅れた場合も、次の接続や操作の前に期限を確認し、期限切れの状態を配信しない。

`idle`へ戻すときは`accepting`以外のセッション状態を初期値へ戻す。`accepting`が`false`の間、iPadは待機画面の代わりに受付停止を表示し、新しい診断を開始できない。

選定を待っていたセッションの`judging`が終わった後（強制リセットや時間切れを含む）に届いた選定の結果は使わず、記録も保存しない。

現在の状態で実行できない操作は拒否し、状態を変えない。そのため、同じ操作が二度届いても二度目は拒否される（例: 表示中ではない質問への回答、`idle`以外での開始）。強制リセットの後に古いiPad操作が届いても、診断は復帰しない。

### 8.3 通信

各端末は同一オリジンの`/api/realtime?role={役割}&screen={番号}`へWebSocketで接続する。役割は`controller`、`display`、`photo`、`light`、`sound`、`admin`のいずれかで、`screen`は展示ディスプレイと写真用だけに付ける。`light`は電球の中継（11章）で、展示ディスプレイと同じ範囲の状態を受け取り、コマンドは送れない。`sound`はサウンド用の画面（11.2節）で、展示ディスプレイと同じ範囲に質問の番号を加えた状態を受け取り、コマンドは送れない。メッセージはJSONテキストとする。

| 方向                     | `type`    | 内容                           |
| ------------------------ | --------- | ------------------------------ |
| クライアントからサーバー | `command` | 状態を変える操作               |
| クライアントからサーバー | `ping`    | 5秒ごとの生存確認と時刻計測    |
| クライアントからサーバー | `audio`   | サウンド用の画面の再生状態。管理画面に表示する。ほかの役割からは無視する |
| サーバーからクライアント | `state`   | 役割別の現在状態とサーバー時刻 |
| サーバーからクライアント | `pong`    | `ping`の送信時刻とサーバー時刻 |

- 接続するとすぐ、サーバーが現在状態を`state`で送る。
- 状態が変わると、サーバーは送信元を含む全端末へ`state`を送る。操作を拒否したときは、送信元にだけ現在状態を送る。iPadと管理画面は、`state`が届いた時点で確定待ちの表示を解除する。
- 再送はしない。通信が切れたら、端末は待ち時間を0.5秒から10秒まで倍にしながら接続し直し、接続後に届く状態を正とする。
- 15秒間`pong`が届かない場合も、切断として接続し直す。
- 診断用iPadは複数台つないでも、どれからでも操作できる。運用では一台だけを置く。

役割ごとに送る状態と使える操作は次のとおりとする。

| 役割         | 受け取る状態                                                                                                   | 使える操作                                                   |
| ------------ | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `controller` | 全項目                                                                                                         | `start`、`continue`、`answer`、`back`、`returnToIdle`        |
| `display`    | `answers`、`questionIndex`、`accepting`、`nickname`、`judgeFailed`を除く項目。`result`は色名、二色、写真IDだけ | なし                                                         |
| `photo`      | `display`と同じ                                                                                                | なし                                                         |
| `light`      | `display`と同じ                                                                                                | なし                                                         |
| `admin`      | `answers`と`nickname`を除く項目と、接続中の端末一覧                                                            | `setAccepting`、`forceReset`、`previewColor`、`clearPreview` |

`previewColor`は`idle`でのみ受理し、展示ディスプレイにパレットの確認用の色を表示する。`clearPreview`、`start`、`forceReset`で解除する。

### 8.4 時刻補正

端末は`ping`の往復から「サーバー時刻 - 端末時刻」を求め、直近6回（30秒分）のうち往復時間が最も短い計測の値を使う。展示ディスプレイの演出と結果の切り替えは、この補正済みサーバー時刻で決める。

## 9. 技術スタック

### 9.1 採用技術

| 区分                 | 採用技術                                                      | 採用理由                                                                     |
| -------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 言語                 | TypeScript                                                    | 画面、通信メッセージ、診断定義で同じ型を共有するため                         |
| UIフレームワーク     | Svelte                                                        | iPad、展示、管理、結果ページを少ない実行時コードで実装するため               |
| ビルド・ローカル開発 | Vite                                                          | Svelteのビルドと、開発サーバーへ会場サーバーの処理を組み込む構成を一つで扱うため |
| 会場サーバー         | Node.js（型の除去で直接実行）+ `ws`                           | 施設回線につないだ一台のPCで、Web画面、WebSocket、静的素材を配信するため           |
| リアルタイム同期     | WebSocket                                                     | 一つの展示状態を複数画面へ配信し、更新順序を一か所で確定するため               |
| 状態保存             | SQLite（`node:sqlite`、`data/exhibit.sqlite`）                | 現在状態と結果の記録を一つのファイルに保存し、再起動後も続けられるようにするため |
| 結果ページ           | Cloudflare Workers + Workers KV                               | 来場者が自分の端末で、施設のネットワークの外から結果ページを開けるようにするため（10章） |
| AI                   | Mistral AI（Chat Completions API）                            | 回答全体の読み取り、二色と色名の選定、写真の内容の判定（6.3節）                |
| 認証                 | なし                                                          | 会場サーバーは施設の閉じたネットワークの中だけで使うため（14章）               |
| 照明                 | Matter対応のスマート電球 + matter.js（`@matter/main`）        | 機種に依存しない共通規格で、会場のPCから電球の色を変えるため（11章）         |
| スタイリング         | 展示画面はSvelteのCSS、管理画面はTailwind CSS + shadcn-svelte | 展示固有の表現と、管理画面の作りやすさを分けるため                           |
| パッケージ管理       | pnpm                                                          | 依存関係と実行環境をロックファイルで固定するため                             |
| 単体テスト           | Vitest                                                        | 出力の検証、写真の選定、状態遷移、メッセージ検証をブラウザなしで確認するため |
| E2Eテスト            | Playwright                                                    | iPad、複数ディスプレイ、管理画面を同時に開く実際のフローを確認するため       |

管理画面のTailwind CSSは、展示用の画面に影響しないよう別のチャンクで読み込む。

### 9.2 アプリケーション構成

一つのSvelteアプリで、起動時の`location.pathname`から表示する画面を決める（4章の表）。質問定義、パレット、写真カタログ、AIの設定は`src/data/`、回答の検証、写真の選定、状態遷移は`src/shared/`の共通モジュールに置く。

展示の本体は、施設回線につないだ一台のPCで動かす会場サーバー（`src/server/`）とする。AIへの指示、入力、出力の検証は`src/server/ai/`に置く。会場サーバーは`/api/realtime`と`/result/*`（10.1節）を処理し、それ以外は`pnpm build`の成果物（`dist/`）の静的ファイルとSPAの`index.html`を返す。開発サーバー（`pnpm dev`）にも同じ処理を組み込む（`src/server/vite-plugin.ts`）。

結果ページだけは、来場者が施設のネットワークの外から開けるよう、Cloudflare Workers で動かす結果ページのWorker（`src/results/`）で配信する。会場サーバーは結果が決まるたびに、結果ページへ公開する部分（10.2節）をこのWorkerへ送る（10.1節）。

### 9.3 検証

- Vitestで回答の検証、AIへの入力、AIの出力の検証、写真の段階の組み立て、選定の失敗と時間切れ、状態遷移、二重操作、メッセージ検証、役割別の配信を確認する。AIの呼び出しは偽の送信関数で置き換える。
- Playwrightで展示ディスプレイを1台と3台開いた構成を、仮の選定（`AI_STUB=1`）で実行し、開始、回答、写真割り当て、結果の切り替え、結果ページ、再接続、強制リセットを確認する。
- `pnpm check`、テスト、production buildがすべて成功した状態を本番で使える状態とする。

照明連携は、会場のPCで動かす中継スクリプト（`scripts/light-bridge.ts`）に分ける。会場サーバーは展示ディスプレイと同じ範囲の状態を`light`の役割へ配信するだけで、Matterの処理を診断ロジックへ含めない。電球ごとの色の割り当てと、Matterへ送る値への変換は`src/shared/lights.ts`に置き、Vitestで確認する。

## 10. 結果の受け渡し

MVPはデジタル受け渡しとする。結果画面に、その体験の結果IDを含むQRコードを表示し、読み取るとその結果ページを来場者自身の端末で開く。

### 10.1 公開URLと公開期間

結果ページは、結果ページのWorkerで配信する。カスタムドメインは取得せず、Cloudflareが発行する`https://dpc-school-festival.<subdomain>.workers.dev`を公開元とする。初回デプロイ後に、確定したURLを末尾スラッシュなしで`wrangler.jsonc`の`PUBLIC_ORIGIN`へ設定する。QRコードと結果URLは必ずこの値から作る。会場サーバーも同じ`wrangler.jsonc`を読み、この値を結果の送り先にする。`PUBLIC_ORIGIN`がHTTPSでない場合、または`https://dpc-school-festival.<subdomain>.workers.dev`の形（末尾スラッシュなし）でない場合はproduction buildを失敗させる。

公開終了日時はISO 8601形式のUTC時刻で`RESULTS_PUBLISHED_UNTIL`へ設定する。終了日時より前は結果ページをHTTP 200で返し、以降は`/result/*`をHTTP 410で返す。410ページには展示名と「この展示の結果ページは公開を終了しました」だけを表示する。形式の合わない結果ID、保存されていない結果IDはHTTP 404とする。

結果ページ（`/result/{結果ID}`）はSPAが表示し、内容は`/result/{結果ID}/data`のJSONから読む。どちらも`Cache-Control: no-store`で返す。

結果の受け渡しは次のとおりとする。

- 会場サーバーは、結果の記録を保存した直後に、結果ページへ公開する部分（10.2節）を`PUT ${PUBLIC_ORIGIN}/api/results/{結果ID}`で送る。`Authorization: Bearer {RESULTS_UPLOAD_TOKEN}`を付ける。
- 送る前に送信待ちとしてSQLiteへ保存し、送れたら送信待ちから消す。送れなかった場合（施設回線の切断など）は、会場サーバーの起動時と30秒ごとに送り直す。結果ページのWorkerがHTTP 410（公開期間の終了）、HTTP 400、またはHTTP 413（内容の不備）を返した場合は、再送しても受け付けられないため送り直さない。HTTP 401（トークンの不一致）は設定を直せば送れるため、送信待ちに残す。
- 結果ページのWorkerは、トークンが一致しない場合はHTTP 401、形の合わない内容はHTTP 400で拒否する。配布を許可していない写真のIDと、10.2節にない項目は捨てて保存する。
- Workerは受け取った内容を、結果IDをキーにWorkers KVへ保存し、`RESULTS_PUBLISHED_UNTIL`の時刻に消えるよう期限を付ける。
- 結果は会場サーバーから届くまでに遅れることがあり、Workers KVへの反映にも最大60秒かかる。そのため結果ページのWorkerは、公開期間中で形式の合う結果IDなら、まだ保存していなくても結果ページ（`/result/{結果ID}`）を返し、データ（`/result/{結果ID}/data`）だけをHTTP 404にする。結果ページはデータがHTTP 404の間、「結果を準備しています。このままお待ちください」と表示し、1秒から10秒の間隔で約3分間読み直す。通信の失敗とHTTP 5xxも同じく読み直す。それでも届かなければ「ページが見つかりません」と表示し、読み込み直すボタンを出す。施設回線が切れている間に決まった結果は、回線が戻って送り直されるまで開けない。
- Workerは静的ファイルのうち結果ページに要るもの（`/assets/`、`/fonts/`、配布を許可した写真の`/photos/`）だけを返し、`/result/*`と`/api/results/*`以外のパス（`/`、`/admin`など）はHTTP 404とする。載せるファイルは`pnpm build:results`が`dist/`から`dist-results/`へ集める。
- 会場サーバーも`/result/*`を返す。会場の端末からの確認とE2Eテストのためで、来場者には案内しない。会場サーバーは結果をその場で読めるため、保存していない結果IDはページもHTTP 404とする。

### 10.2 結果ページの内容

結果ページには次だけを含める。回答、写真の選定の根拠、モデル名は含めない。

- 色名と命名理由、二色の混色プレビュー
- 回答の読み取り、二色それぞれの色名と理由、二色の関係
- 選定した写真のうち配布許可済み（`shareAllowed: true`）の写真と、その作者クレジット（`© {creditName}`）
- 展示名と開催情報

配布を許可する写真には`creditName`を必須とし、ない場合はproduction buildを失敗させる。写真を読み込めない場合は、その写真とクレジットを隠す。

### 10.3 QRコード

QRコードへ格納する文字列は`${PUBLIC_ORIGIN}/result/${結果ID}`だけとし、セッションIDや回答内容を含めない。結果IDは体験ごとに異なり、推測されにくい値にする（6.4節）。

- iPad上でSVGとして生成し、外部のQR生成APIへURLを送らない。表示サイズは256 × 256 CSS px、前景`#000000`、背景`#FFFFFF`、Quiet Zoneは4 modules、誤り訂正レベルはMとする。
- QRコードの直下に、同じ結果URLをテキストで表示する。
- 生成に失敗した場合は、QRコードの代わりに「QRコードを表示できませんでした」と結果URLを表示する。結果表示と60秒のタイマーは止めない。

公開前に通し診断で表示したQRコードを本番のiPadへ表示し、iPhoneとAndroidの標準カメラで読み取れることを会場の照明で確認する。

## 11. 照明・装飾連携

Matter対応のスマート電球を、会場サーバーと同じPCで動かす中継スクリプト（`scripts/light-bridge.ts`、`pnpm lights`）で操作する。Matterの処理を会場サーバーへ含めないため、中継スクリプトが会場サーバーの`/api/realtime?role=light`へ接続して展示状態を受け取り、同じ施設のネットワークの電球へMatterの命令を送る。Matterの操作には matter.js（`@matter/main`）を使う。

- 通常は白色（約4000K）にする。結果の表示中（`result`）は、AIが選んだ二色を電球の並び順に交互に割り当てる（電球kは`result.colors[k % 2]`、kは0始まり）。展示ディスプレイの割り当て（7.2.4節）と同じ規則とする。
- 待機中に管理画面の表示確認を使うと、全部の電球をその色にする。表示確認をやめると白色へ戻す。
- 白色から色へは3秒、色から白色へは2秒かけて移す。強制リセットと待機への遷移でも白色へ戻す。
- 色は、パレットの色（sRGB）から計算したCIE 1931の色度座標（xy）と既定の明るさ（254）で送る。会場で電球を見ながら色ごとに調整した照明シーン（色度座標と明るさの一方または両方）を`src/data/lights.ts`の`colors`に書くと、書いた項目だけを上書きする。明るさは1〜254に収めて送る。xy色空間に対応しない電球は、色度座標の代わりにパレットのHと、HSLからHSVへ直した彩度で送る（`colors`の`xy`は使わない）。その電球の白色は、色温度に対応していれば4000K（250ミレッド）、対応していなければ彩度0で送る。
- 電球の並び順は、`pnpm lights pair`で登録した順とする。一つの機器に色を変えられるエンドポイントが複数あれば、エンドポイント番号の順にそれぞれを電球一つとして数える。
- 電球へ送れなかったときは、つながっている電球には5秒ごとに、切れた電球にはつながり直したときに、その時点の色を送り直す。中継スクリプトが展示に接続できない間は、最後の色のまま待つ。
- 電球のアプリや壁のスイッチで電球が消されたときは、5秒以内に点け直す。色や明るさだけを変えられたときは、次に段階が切り替わるまで直さない。
- 電球や中継スクリプトが失敗しても、画面上の診断は止めない。
- 強い高速点滅は使わない。`pnpm lights identify`による点滅は、開場前に電球の番号を確かめるときだけに使う。

### 11.1 電球の登録（設営時に一度）

電球は、中継スクリプトを動かすPCと同じネットワークにつないでおく。スマートフォンのアプリで設定済みの電球は、そのアプリの「他のアプリと共有」などで出るペアリングコードを使う。Bluetoothでの初期設定は中継スクリプトでは行わない。

| コマンド                              | 内容                                                         |
| ------------------------------------- | ------------------------------------------------------------ |
| `pnpm lights pair <ペアリングコード>` | 電球を登録する。11桁の数字か`MT:`から始まるQRコードの文字列  |
| `pnpm lights list`                    | 登録した電球を並び順に表示する                               |
| `pnpm lights identify <番号>`         | その番号の電球を10秒点滅させる（Identifyに対応する電球だけ） |
| `pnpm lights remove <番号>`           | その番号の電球の登録を外す                                   |
| `pnpm lights`                         | 展示状態に合わせて電球を動かす                               |

並び順を変えるときは、登録を外して望む順に登録し直す。登録の記録（コントローラーの鍵と電球）はリポジトリ直下の`.matter-lights/`に保存する（`MATTER_STORAGE_PATH`で変えられる）。このフォルダーはコミットしない。`pnpm lights`で電球を動かしている間は、同じ記録を使うほかのコマンドを使えないため、先に止める。

中継スクリプトの設定は、環境変数か`.env.lights`で渡す（`.env.lights.example`）。

| 環境変数                  | 内容                                                                     |
| ------------------------- | ------------------------------------------------------------------------ |
| `LIGHT_ORIGIN`            | 任意。会場サーバーのURL（末尾スラッシュなし）。既定は同じPCの`http://localhost:8787`。開発サーバーなら`http://localhost:5173` |
| `MATTER_STORAGE_PATH`     | 任意。登録の記録の保存先。既定はリポジトリ直下の`.matter-lights/`        |

### 11.2 サウンド演出

音の正本は`refs/サウンド実装引き継ぎ`（v1.5、2026-11-25）の`handoff/サウンド演出仕様と実装引き継ぎ.md`と`playback-config.json`とする。音は会場のスピーカーにつないだPCのChromeで開くサウンド用の画面（`/sound`）だけが鳴らす。展示ディスプレイは複数台あり、全部で鳴らすと重なるため鳴らさない。iPadも鳴らさない。サウンド用の画面は`/api/realtime?role=sound`へ接続し、展示ディスプレイと同じ範囲の状態に質問の番号を加えて受け取る（回答内容とニックネームは受け取らない）。

| 系統 | 音源 | 鳴らすとき |
| ---- | ---- | ---------- |
| BGM | BGM01.m4a（約16分17秒） | 画面を開いている間ずっとループする。画面の段階が変わっても先頭へ戻さず、重複して起動しない |
| ガラス音 | 遠く小さく鳴る18種類 | 画面を開いている間ずっと、鳴り始めから次の鳴り始めまで5〜7秒の間隔でランダムに鳴らす。18種類を一巡するまで同じ音を使わず、一巡の境界でも同じ音を続けない。余韻の重なりを許す。音量0.63、発音ごとにHRTFで位置を変える（x −3.5〜3.5、y −1〜1、z −6〜−1、距離による減衰なし）。コンプレッサー（threshold −10 dB、knee 12 dB、ratio 6）を通す。60秒の完成WAVのループでは代用しない |
| ナレーション | 1〜12.wav | 「はじめる」で1〜4.wav（ようこそ、企画説明、体験への導入、ニックネーム入力）を続けて読む。質問へ入るとその質問の分を読む（下表）。`judging`へ入ると11.wav、`result`へ入ると1.5秒後に12.wav |
| 回答SE | Q1〜Q6.caf | 回答を受け付けたとき。ニックネームの送信でQ1、質問の回答でQ2〜Q6（下表）。低い音から順に上がる |
| 完了SE | Complete_v13_open_chord.caf | `result`へ入ると同時に1回 |

引き継ぎ資料の「Q1〜Q6」はニックネーム入力をQ1、内容の質問をQ2〜Q6と数える。このアプリの質問IDは内容の質問だけを`Q1`〜`Q5`と数えるため、一つずれる。対応は`src/data/sound.ts`の`SOUND_CUES`に書く。

| アプリの質問ID | 引き継ぎ資料の番号と場面 | ナレーション | 回答SE |
| -------------- | ------------------------ | ------------ | ------ |
| （`intro`） | Q1 ニックネーム入力 | 4.wav（1〜3.wavに続けて読む） | Q1.caf |
| `Q1` | Q2 過ごしたい時間 | 5.wav | Q2.caf |
| `Q2` | Q3 幸せを感じる瞬間 | 6.wav | Q3.caf |
| `Q3` | Q4 物事への向き合い方 | 7.wav（質問）、8.wav（操作案内） | Q4.caf |
| `Q4` | Q5 今の心の状態 | 9.wav | Q5.caf |
| `Q5` | Q6 展示後の気持ち | 10.wav | Q6.caf |

- 鳴らす音は、直前に受け取った状態からの変化で決める（`src/shared/sound.ts`）。状態は受理のたびに`revision`が1増えるため、`revision`が飛んだとき（切断中に進んだとき）と画面を開いた直後は、過ぎた出来事を後から鳴らさない。同じ出来事を二度鳴らさない。
- 回答SEは、iPadの「次へ」をサーバーが受理した時点で鳴らす。会場のネットワークの往復の分だけ遅れるが、AIの選定や結果の送信は待たない。
- 次の場面のナレーションを読むときは、読んでいるナレーションを0.4秒でフェードアウトしてから読む。続けて読むナレーションの間は0.4秒あける。
- 質問から質問へ移る（回答して次へ進む、「戻る」）ときは、iPadが前の質問を落としてから次の質問を降ろし始める時刻（`QUESTION_ENTER_DELAY_MS`、1.66秒後）に合わせて読み始める（`SOUND_MIX.questionSwitchNarrationDelayMs`。値の一致は`tests/unit/sound.test.ts`が確かめる）。`intro`から最初の質問へ入るときは待たない。iPadの「視差効果を減らす」を有効にすると質問が即時に出るため、会場のiPadでは無効にしておく。
- 「戻る」で前の質問へ戻ると、その質問のナレーションを読み直す（回答SEは鳴らさない）。答え直すと、その質問の回答SEをもう一度鳴らす。
- AIの選定に失敗して最終問へ戻ると、11.wavを止め、質問のナレーションは読み直さない。もう一度送ると、Q6.cafと11.wavを鳴らす。
- 待機へ戻る（「最初に戻る」、60秒経過、強制リセット、5分の放置）と、ナレーションを止める。BGMとガラス音は止めない。
- `/sound`の「すべての音を止める」で、BGM、ガラス音、ナレーション、効果音を即座に止める。止めている間は展示の進行の音も鳴らさない。「音を再開する」でBGMとガラス音が鳴り直し、ナレーションと効果音は次の進行から鳴る。この状態はそのページを開いている間だけ持つ（再読み込みで解除する）。
- ナレーションを読んでいる間は、BGMを0.6倍、ガラス音を0.8倍へ下げる（0.4秒で下げ、1.2秒で戻す）。
- 音量、減音の倍率、間の長さは仮の値で、`src/data/sound.ts`の`SOUND_MIX`に書く。会場では`/sound`の画面で系統ごと（全体、BGM、ガラス音、ナレーション、回答SE・完了SE）の倍率を調整できる。調整はそのブラウザに保存する。
- ブラウザが自動再生を止めているときは、画面の「音を出す」か、画面のどこかをクリックすると鳴り始める。Chromeを`--autoplay-policy=no-user-gesture-required`を付けて起動すれば、再読み込みの後もクリックなしで鳴る。
- 読み込めない音源があっても、残りの音で続ける。音が出なくても、診断と結果表示は止めない。

音源は`refs/サウンド実装引き継ぎ/assets`の原本から`pnpm export-sounds`で`public/sounds/`へ書き出す（ffmpegとlibopusが必要）。BGMはAACのままコピーし、それ以外はOpus（Ogg、48kHz、ステレオ）へ変換する。ChromeはCAFを再生できず、96kHzのWAVは容量が大きいためである。原本は変えない。書き出した音源の欠落はproduction buildを失敗させる。BGMの`<audio>`は範囲を指定して読むため、会場サーバーは`Range`に応じる。

## 12. 写真素材の要件

### 12.1 表示用ファイル

- 原本は表示用ファイルと分けて保管し、Webアプリから直接配信しない。
- 写真IDは小文字ASCII英数字をハイフンで区切った形式（`^[a-z0-9]+(?:-[a-z0-9]+)*$`）とする。
- 一つの写真IDから`public/photos/{photoId}.avif`と`public/photos/{photoId}.jpg`の二ファイルを`pnpm export-photos`で書き出す。AVIFを優先し、読み込めないブラウザにはJPEGを表示する。
- 両形式は同じ原本から生成した、回転情報を反映したsRGB画像とする。
- 長辺は3,840px以下とし、原本より大きくしない。一ファイルの上限はAVIF 2MiB、JPEG 3MiBとする。欠落、上限超過、二形式の寸法の不一致はproduction buildを失敗させる。

### 12.2 メタデータと画面割り当て

- 写真カタログ（`src/data/photos.ts`）の各写真に、一意の写真ID、寸法、`idleEnabled`、`idleOrder`、`shareAllowed`、`creditName`、任意の`creditUrl`と、選定に使うタグを設定する（handoffの`examples/photo-catalog.json`）。
  - `colorTags.overall`: 写真全体の印象に合うパレットの色ID
  - `colorTags.partial`: 視認できる一部分に合うパレットの色ID
  - `contentTags`、`moodTags`: 写っているものと雰囲気の語
  - `description`: 写真の短い説明
  - `tagStatus`: `provisional`（仮）または`confirmed`（写真担当が確認済み）
- 色タグはAIへ渡さず、実装側の色の適合の判定（6.3節）に使う。内容のタグ、雰囲気のタグ、説明はAIへ渡す。
- 写真定義には画面番号を持たせない。待機表示は`displayOrder`と`idleOrder`、結果表示は`displayOrder`と選定の順で割り当てる。
- 写真IDの重複、ファイルの欠落、パレットにない色タグはproduction buildを失敗させる。
- 展示用データへ文字やUIを焼き込まない。

### 12.3 色の実機確認

会場の照明の下で、全展示ディスプレイと本番のiPadにパレットの13色の色面と写真を表示し（管理画面の表示確認を使う。電球も同じ色になる）、写真担当と企画担当の二名が、白飛び・黒つぶれ、意図しない色かぶり、隣の色と区別できない状態がないことを確認する。あわせて電球の13色の見え方を確認し、必要なら`src/data/lights.ts`の`colors`を調整する。自動輝度、Night Shift、True Toneは切る。

## 13. プライバシーとアクセシビリティ

- 個人を特定できる情報を入力させない。`intro`で入力するのは来場者が自由に決めるニックネームで、本名を求めない。
- ニックネームは`src/shared/nickname.ts`で正規化する（NFC正規化、制御文字と書式文字の除去、空白の圧縮、前後の空白の除去）。空、または12文字を超える場合は受け付けない。保存は`intro`の送信から`idle`へ戻るまでとする。ニックネームは診断用iPadにだけ配信し、展示ディスプレイ、写真用、管理画面には配信しない。
- 展示状態の回答は、再読み込みからの復帰とAIの選定のため、`intro`から選定が終わるまで会場サーバーのSQLiteへ保存する。選定の結果を設定するとき、同じ状態更新で展示状態の`answers`を消去する。放置された回答は5分後の自動リセットで、強制リセットでは即時に消去する。
- 選定が成功した体験の回答は、結果の記録（6.4節）として会場サーバーのSQLiteに残す。記録にはニックネームを含めない。結果ページのWorkerへは回答を送らず、結果ページからは回答を読めない。記録を消す時期は16章で決める。
- アクセスログは作らない。障害時に原因を調べられるよう、会場サーバーのログには回答が残ってよい。AIのエラー応答と、検証に通らなかった返答の本文は、そのままログに出す。
- 最終回答はAIの選定のため Mistral AI へ送る。ニックネームは送らない。APIに保存を止めるリクエスト単位の指定はないため、Mistral AI の管理画面でデータの扱い（学習への利用の停止など）を設定しておく。
- AIへの指示では、回答だけを根拠とし、職業、年齢、性別、疾患、過去などを推測しないこと、性格を断定しないこと、内向きや低エネルギーを否定的に扱わないことを求める（handoff 5章、7章）。
- 操作UIは色覚だけに依存しない。`prefers-reduced-motion: reduce`では大きな動きを抑える。
- 音声は体験成立の必須要素にしない。ナレーションと効果音が鳴らなくても、画面の文言と操作だけで診断を終えられる。

## 14. 当日運用

### 会場サーバーの構成

展示の本体は、施設回線につないだ一台のPC（会場サーバー）で動かす。iPad、展示ディスプレイ、写真用、管理画面は、同じ施設のネットワークから会場サーバーのアドレスを開く（例: `http://192.168.1.2:8787/display/1`）。

- アプリには認証がない。会場サーバーは施設の閉じたネットワークの中だけで使い、ポートをインターネットへ公開しない。来場者のスマートフォンを同じネットワークへつながせない。
- 会場サーバーのアドレスが変わらないよう、施設のルーターでIPアドレスを固定するか、DHCPの予約を設定する。
- 会場サーバーはAIの選定（Mistral AI）と結果の送信（10.1節）のため、施設回線からインターネットへ出られる必要がある。

### 結果ページのWorkerのデプロイ（初回と設定の変更時）

1. `pnpm exec wrangler login`でCloudflareアカウントにログインする。
2. `pnpm exec wrangler kv namespace create RESULTS`でKVの名前空間を作り、表示された`id`を`wrangler.jsonc`の`kv_namespaces`へ書く。公開終了日時（16章）を`wrangler.jsonc`の`RESULTS_PUBLISHED_UNTIL`へ書く。
3. 推測されにくいトークンを作り（例: `node -e "console.log(crypto.randomUUID())"`）、`pnpm exec wrangler secret put RESULTS_UPLOAD_TOKEN`で設定する。会場サーバーの`.env`にも同じ値を書く。
4. `pnpm deploy:results`でデプロイする（`pnpm build`、`pnpm build:results`、`wrangler deploy`の順に実行する）。
5. 初回は、確定したworkers.devのURLを末尾スラッシュなしで`wrangler.jsonc`の`PUBLIC_ORIGIN`へ書き、もう一度`pnpm deploy:results`を実行する。会場サーバーを起動済みなら、`pnpm build`し直して再起動する（QRコードのURLはビルド時に埋め込み、結果の送り先は起動時に`wrangler.jsonc`から読むため）。

写真の配布許可（`shareAllowed`）を変えたときも、`pnpm deploy:results`をやり直す。

`wrangler.jsonc`ではバージョンごとのプレビューURLを無効にしている。結果の受け取り口を増やさないためである。

### 会場サーバーの起動

1. Node.js（`.node-version`の版）とpnpmを入れ、`pnpm install`を実行する。
2. `.env.example`を`.env`へコピーし、下記「環境変数」の値を書く。
3. 音源を変えたときは`pnpm export-sounds`で`public/sounds/`へ書き出す（11.2節）。`pnpm build`で画面をビルドする。
4. `pnpm start`で起動する。起動すると、各端末から開くアドレス（`http://{IPアドレス}:8787/`）を表示する。

展示状態と結果の記録は`data/exhibit.sqlite`に保存するため、会場サーバーを再起動しても、展示状態と送信待ちの結果を引き継ぐ。PCのスリープと自動更新による再起動は、開場中は止めておく。

### 環境変数（会場サーバーの`.env`）

| 環境変数               | 設定方法                                | 内容                                                                       |
| ---------------------- | --------------------------------------- | -------------------------------------------------------------------------- |
| `MISTRAL_API_KEY`      | 必須                                    | APIキー。なければAIの選定ができず、結果を出せない                          |
| `MISTRAL_MODEL`        | 任意                                    | モデルID。既定は`mistral-small-latest`                                     |
| `MISTRAL_BASE_URL`     | 任意                                    | ベースURLの上書き。既定は`https://api.mistral.ai/v1`                       |
| `RESULTS_UPLOAD_TOKEN` | 必須。結果ページのWorkerと同じ値        | 結果を結果ページのWorkerへ送るトークン。なければ結果を送らない             |
| `PORT`、`HOST`         | 任意                                    | 待ち受けるポートとアドレス。既定は`8787`と`0.0.0.0`                        |
| `DATA_FILE`            | 任意                                    | SQLiteのファイル。既定は`data/exhibit.sqlite`                              |
| `AI_STUB`              | 開発とE2Eテストだけ。本番では設定しない | `1`ならAIへ接続せず、決まった二色を返す仮の選定を使う。APIキーより優先する |

`AI_STUB`の結果は色名を「開発用の仮の色」とし、本番の結果と見分けられるようにしている。E2Eテストの開発サーバーは`AI_STUB=1`で起動する（`vite.config.ts`）。

開発サーバー（`pnpm dev`）も`.env`を読む。展示状態は`data/dev.sqlite`に分けて保存し、開発中の結果が来場者向けの結果ページに載らないよう、`RESULTS_UPLOAD_TOKEN`があっても結果を送らない。

### 開場前

1. 会場サーバーを起動し（`pnpm start`）、全端末を同じ施設のネットワークへ接続して、会場サーバーのアドレスで4章のURLを開く。展示ディスプレイは来場者から見た順に番号を振る。
2. 会場サーバーと同じPCで`pnpm lights`を動かし、全部の電球が白色になることを確かめる。スピーカーにつないだPCのChromeで`/sound`を一つだけ開き、「音を出す」を押す。管理画面で、iPad、全展示ディスプレイ、全写真用、電球の中継、サウンドが「接続中」で、サウンドの音が「再生中」であることを確認する。
3. 管理画面の表示確認で13色を表示し、画面と電球の色の対応を確認する。電球の並び（一色目と二色目が交互になる配置）を`pnpm lights list`と`pnpm lights identify`で確かめる。
4. 一回の通し診断を行い、AIの選定で結果が出ること（色名が「開発用の仮の色」でないこと）を確かめる。「最初に戻る」で全画面が待機へ戻れば開場可能とする。
5. 施設のネットワークにつないでいないスマートフォン（モバイル回線）で、手順4のQRコードから結果ページが開けることを確認する。同じスマートフォンで`PUBLIC_ORIGIN`の`/`と`/admin`がHTTP 404になることも確認する。
6. 会場サーバーのログに「結果 {結果ID} を結果ページへ送れませんでした」というエラーが出ていないことを確認する。

### 障害時

- 一画面だけおかしい場合は、そのブラウザを再読み込みする。
- 全画面が同期しない場合は、受付を停止し、管理画面から強制リセットする。
- QRコードだけが表示されない場合は、iPadに出る結果URLで案内を続ける。
- AIの選定の失敗が続く場合（iPadに「色をうまく選べませんでした」という表示が繰り返し出る）は、受付を停止し、会場サーバーのログで原因（APIキー、レート制限、Mistral AI の障害、施設回線の切断）を確かめる。固定の結果へ切り替える手段は持たない。
- 施設回線だけが切れた場合、会場サーバーと各端末は施設のネットワークで動き続けるが、AIの選定ができないため結果を出せない。受付を停止し、回線が戻るのを待つ。回線が戻れば、送れなかった結果は自動で送り直す。
- 会場サーバーが止まった場合は、`pnpm start`で起動し直す。各端末は自動で接続し直し、保存した展示状態から続ける。会場サーバーは一件の処理の失敗では止まらず、ログに「想定外の例外が起きました」と出して動き続ける。
- 会場サーバーは起動時に、`wrangler.jsonc`の`PUBLIC_ORIGIN`や`RESULTS_PUBLISHED_UNTIL`に誤り（仮の値のまま、期限切れなど）がある場合や、`RESULTS_UPLOAD_TOKEN`や`MISTRAL_API_KEY`が未設定の場合は、警告をログに出す。開場前にこれらの警告がログに出ていないことを確かめる。
- 管理画面のサウンドが「クリック待ち」なら、`/sound`の画面をクリックする。「一部の音源なし」なら、`/sound`の画面に出る音源を`pnpm export-sounds`で書き出し、`pnpm build`し直して再読み込みする。音が止まっても診断は続けられる。
- 照明だけが失敗した場合は、照明連携を止めて画面展示を続ける。中継スクリプトを止めると、電球は最後の色のまま残るため、電球のアプリでの操作か電源の入れ直しで白色へ戻す。
- 一つの電球だけが色を変えない場合は、中継スクリプトのログで「送れませんでした」を含む行を探し、電球の電源とネットワークを確かめる。つながり直せば、その時点の色を送り直す。

## 15. 受け入れ条件

自動テストで確認するもの:

- 5問の質問IDと入力方式がhandoffと一致する。複数選択は選択数の範囲、単独選択の切り替え、上限での選択の停止、順位つき選択は選んだ順の保持と繰り上がりを守る。スライダーと2Dマップは真ん中から始まり、そのまま送れる。入力の操作だけでは`revision`が増えず、「次へ」で一度だけ回答が受理される。
- 戻る操作で直前の回答が復元され、変更して再確定すると変更後の回答だけがAIの選定へ渡る。
- 入力方式に合わない回答は受理されない。
- AIへの入力に質問文、回答の文言、軸の語と値を含み、ニックネームを含まない。
- AIの出力の検証が、パレットにない色、同じ色、自由なh/s/l、二色の列挙の色名、文字数超過、無効な質問IDを拒否する。
- 写真は段階1→2→3の順に選ばれ、カタログにない写真と重複を使わず、不足枚数が記録される。
- 色の選定に失敗したら一度やり直し、それでも失敗したら固定の結果を作らずに最終問へ戻る。写真の選定に失敗しても二色は変わらない。
- 最終回答が二度届いても、選定は一度だけ行う。選定の途中で強制リセットや時間切れになったら、後から届いた結果を使わない。
- 展示ディスプレイ1台と3台の両方で、全画面が同時に結果へ切り替わり、画面ごとに二色を交互に見せる。展示ディスプレイは写真を表示しない。
- 結果表示中に再読み込みした展示ディスプレイは、結果演出を再生せず完了状態を表示する。
- 展示ディスプレイは待機中も質問中も結果表示中も破片の群れを描き、写真と展示タイトルを表示しない。写真用は待機用プレイリストを8秒ごとに巡回する。
- `.avif`の取得に失敗しても、同じ写真のJPEGを表示する。
- 「最初に戻る」で全端末が待機表示へ戻り、`result`開始から60秒後には操作がなくても待機表示へ戻る。
- 強制リセット後、回答、結果、QRコードが次の来場者へ残らない。強制リセットの後に届いたiPad操作で診断が復帰しない。
- `intro`または`question`で5分間操作しない場合、`idle`へ戻って回答を消去する。
- 選定の結果を設定した直後、保存した展示状態の`answers`が空になる。
- 展示ディスプレイ、写真用、電球の中継、管理画面には回答内容とニックネームが届かない。展示ディスプレイと電球の中継には結果IDと読み取りも届かない。電球の中継は状態を変えるコマンドを送れない。
- 電球は、結果の表示中は二色を並び順に交互に、待機中の表示確認では確認中の色に、それ以外は白色になる。`src/data/lights.ts`の`colors`に書いた照明シーンは、書いた項目（色度座標、明るさ）だけを上書きする。
- サウンド用の画面は、一回の体験でナレーション、回答SE、完了SEを11.2節の対応で一度ずつ鳴らす。「戻る」、選定の失敗、待機への遷移では11.2節のとおりにする。画面を開いた直後と切断から戻った直後は、過ぎた出来事を鳴らさない。ガラス音は18種類を一巡するまで重複させず、一巡の境界で同じ音を続けない。全音源を読み込んで「再生中」になり、その再生状態を管理画面へ知らせる。サウンド用の画面には回答内容とニックネームが届かない。
- 通信が切れたiPadは操作できず、復旧後はサーバーの状態を表示する。
- 切断した展示ディスプレイは管理画面で「切断」になり、再接続すると「接続中」へ戻る。
- 結果ページは保存した結果を表示し、配布を許可した写真だけを出す。結果ページのデータに回答と写真の根拠を含まない。形式の合わない結果IDと保存されていない結果IDはHTTP 404、`RESULTS_PUBLISHED_UNTIL`以降はHTTP 410になる。
- 結果ページのWorkerは、トークンの合わない送信と形の合わない結果を拒否し、配布を許可していない写真を公開しない。まだ届いていない結果は、ページを返してデータだけをHTTP 404にする。結果ページ以外の画面のパス（`/`、`/admin`など）はHTTP 404にする。
- 会場サーバーは、送れなかった結果を送信待ちに残し、送り直す。

会場で確認するもの:

- 14章「開場前」の手順をすべて満たす。
- 通し診断のQRコードを、iPhoneとAndroidの標準カメラで読み取れる。
- 本番のAPIキーで、AIの選定が30秒の上限内に終わる。
- 12.3節の色の確認を、写真担当と企画担当の両名が承認する。
- 本番の電球が、通し診断の結果の二色に変わり、「最初に戻る」で白色へ戻る。
- 会場のスピーカーで通し診断を行い、BGMとガラス音が途切れず、ナレーションが聞き取れ、回答SEと完了SEが鳴ることを確かめる。系統ごとの音量と、ナレーション中の減音を決める（11.2節）。
- 本番のiPadで`intro`、最長文の`question`、`judging`、`result`を縦向きと横向きで表示し、横スクロールや要素の重なりがなく、主操作に届く。
