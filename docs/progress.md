## 判断に迷った点

ユーザーの判断が必要な点。実装はそれぞれ下記の仮の判断で進めている。

1. **管理画面への先読み報告と時刻同期精度の送り方**（仕様書7.2.5節、8.6節）。仕様書は管理画面への報告を求めているが、8.5節のメッセージ表に該当する種類がない。`diagnostic` に `preloadReport` と `clockSync` を追加して送っている（`src/shared/protocol.ts`）。8.5節の表では `diagnostic` は診断用iPadから送るものになっている点も含めて決定が必要。
2. **管理画面とペアリングのHTTP API**。仕様書9.2節は `/api/pair` と `/api/realtime` だけを挙げるが、8.4節の管理セッションの発行、コード発行、端末セッション一覧と失効、端末の初期画面での登録確認にはHTTPの入口が要る。`/api/admin/session`、`/api/admin/pairing-codes`、`/api/admin/sessions`、`/api/admin/sessions/{id}`、`/api/session` を追加した。
3. **`releaseController` で `revision` を増やすか**。展示状態（8章）を変えないため増やしていない。15章「受理した各更新により1ずつ増え」の「更新」を展示状態の更新と解釈した。
4. **close code が決まっていない切断**。JSONでないメッセージとバイナリフレームは1007、15秒無通信は1001で閉じている（8.5節の表に定めがない）。
5. **`intro` 中に新しく接続した展示ディスプレイの待機巡回の基準時刻**。`cycleIndex` は `idle.phaseStartedAt` から求めるが、展示ディスプレイへ配信する状態には `idle` の開始時刻が残らない。`intro` の `phaseStartedAt` を基準にしている。
6. **結果開始後に接続した展示ディスプレイの写真**。7.2.5節「結果開始時刻までに読み込めなかった画面はタイポグラフィ」をそのまま当てはめると、結果表示中に再読み込みした画面は必ずタイポグラフィになる。演出を再生しない画面（7.2.4節）は、割り当て写真の読み込みが終わった時点で写真かタイポグラフィかを決め、以後は変えない。
7. **展示一画面構成のE2E**。9.5節の「展示一画面と展示三画面の二構成」は、展示ディスプレイを1台と3台登録して実行している。
8. **WebSocket Upgradeの401/403のE2E**。ローカル開発サーバー（Cloudflare Vite plugin）はUpgrade要求へのWorkerの101以外の応答を中継せずソケットを閉じる。E2EではUpgradeで接続が成立しないことと、同じ要求をUpgradeなしで送ったときのWorkerの401/403を確かめ、役割別の判定は単体テストで確かめている。
9. **QRコード生成失敗のE2E**。生成処理を失敗させる手段が実装にないため、再試行と失敗時の流れは単体テストで、`diagnostic` から管理画面の `alert` までの流れはE2Eで確かめている。iPadの代替表示（結果URL）はE2Eで確かめていない。
10. **配点の偏り**。仮の配点で78,125通りの分布は最小10.85%（green）から最大14.43%（blue）。「極端な偏り」の基準が仕様書にないため、テストは全色が一度は出ることだけを確かめている（`pnpm distribution` で分布を表示）。
11. **仮の `PUBLIC_ORIGIN` でもproduction buildが通る**。ビルド時に確かめられるのはHTTPS、末尾スラッシュなし、`dpc-school-festival.<subdomain>.workers.dev` の形までで、subdomainが実在するかはアカウント情報がないと確かめられない。仮値 `tbd-subdomain` のままデプロイしないこと。
12. **冪等性記録と回答の消去**。最終回答の受理、強制リセット、放置による初期化で回答を消去するとき、回答を含む冪等性記録も消している（13章）。消した要求を10分以内に再送されると保存済みの応答ではなく `STALE_REVISION` を返す（状態は変わらない）。8.5節「同じ応答を返す」とのずれで、プライバシー要件を優先した。
13. **写真の結果色の割り当て（仮）**。提供された12点の `resultColorId`、各色の代表画像、`shareAllowed`、`creditName`、`idleOrder` は、写真の主題から仮に決めた値（`src/data/photos.ts`）。写真担当責任者による決定が必要。現在の割り当て: red `sdi1218-3`、orange `sdi0743`、yellow `sdi1092-2`、green `sdi0225` `sdi0776`、cyan `sdi0565-2` `sdi1091`、blue `sdi1195-3` `sdi1134-2`、violet `sdi1031-2` `sdi1163-3`、magenta `sdi1070-2`。各色1〜2点のため、3画面構成では写真のない画面が色名のタイポグラフィになる（12.2節の目安は各色「展示ディスプレイ数 + 2」点以上）。
14. **写真の長辺**。仕様書12.1節を「3,840px以下、原本より大きくしない」に改めた。表示用は原本の寸法（長辺2048px）のまま書き出している。4Kディスプレイでは拡大表示になる。
15. **原本の管理**。`photos/originals/` はリポジトリへコミットしていない。原本をリポジトリで管理するか、別の場所に保管するかの決定が必要。
16. **`displayManifest` の廃止（ユーザーの指示による仕様変更。仕様書へ反映済み）**。仕様書7.2節は台数を `displayManifest` の登録件数とし、画面IDを管理画面で選ぶ形にしているが、登録簿なしで、端末登録した展示ディスプレイの台数で動くようにした。
    - 展示ディスプレイのペアリングコードは画面を指定せずに発行し、登録時にサーバーが使用中でない最小の番号の画面ID（`display-1`、`display-2`…）を振る。並び順（`displayOrder`）はその番号の順で、写真の割り当て、待機の巡回、質問中の輪のずれに使う。来場者から見た順に登録する必要がある。
    - 台数は有効な端末セッションを持つ展示ディスプレイの数。管理画面の端末一覧と結果同期の計測対象はこの一覧から作る。失効させた番号は次の登録で再利用する。
    - 画面の向きと解像度の登録がなくなったため、写真の長辺の上限は3,840pxだけを確かめる（上記14）。
    - 仕様書（docs/README.md）の7.2節、7.2.1節、8.4節、9.4節、9.5節、12.1節、12.2節、12.3節、13章、15章、16章を、この変更に合わせて書き換えた。
