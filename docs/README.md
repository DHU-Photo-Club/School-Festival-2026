# あなた色写真展 - 診断インタラクティブ展示 - 仕様書

## 1. 文書の位置づけ

本書は、学園祭で一度だけ実施するあなた色診断展示の企画・制作・当日運用における基準とする。
未確定事項は16章「要決定事項」に集約し、それ以外はMVPの暫定仕様として実装を進める。

一回きりの学内展示なので、当日に止まらず、止まってもスタッフがすぐ戻せることを優先する。公開サービス向けの冗長な仕組み（再送、冪等性、端末認証、計測の記録など）は持たない。

## 2. 体験の目的

来場者が直感的な質問に答えると、その回答から一つの「今の自分を表す色」が決まり、写真・画面・教室内の光が同じ色へ変化する体験を提供する。
この診断は、展示作品として楽しむためのものとする。「似合う色」の断定ではなく、「回答から選ばれたあなたの色」と表現する。

### 体験完了の条件

- 来場者が説明を受けなくても、開始から結果表示まで一人で操作できる。
- 結果の色、色名、短いメッセージが同時に表示される。
- 結果表示に合わせて、すべての展示ディスプレイが同じ結果へ切り替わる。
- 次の来場者が前の回答を見ずに、新しい診断を開始できる。

## 3. MVPの範囲

### 実施するもの

- iPad上での診断操作
- 選択回答に基づく結果色の決定
- 複数ディスプレイへの同期表示
- 結果色に対応する写真作品の表示
- 結果画面からのデジタル結果受け渡し
- スタッフによる強制リセットと接続状態の確認

### MVPでは実施しないもの

- 氏名、年齢、連絡先などの個人情報収集（`intro`で入力するニックネームは来場者が自由に決める呼び名で、本名を求めない）
- カメラや顔画像を用いた自動診断
- 来場者自身による写真投稿
- AIによる診断文や画像のリアルタイム生成
- フルカラー印刷
- 複数人の同時診断

即時印刷と高度な照明制御は、機材と現地検証の結果を踏まえて追加する。

## 4. 利用者と端末

| 種別             | 役割                     | 開くURL                          |
| ---------------- | ------------------------ | -------------------------------- |
| 来場者           | 診断を受ける             | iPadで回答し、QRで結果を受け取る |
| 診断用iPad       | 診断を操作する           | `/`                              |
| 展示ディスプレイ | 写真作品と演出を表示する | `/display/1`、`/display/2`…      |
| 写真用           | 写真だけを巡回表示する   | `/photo/1`、`/photo/2`…          |
| 運営スタッフ     | 当日の進行と復旧を行う   | `/admin`                         |
| 結果ページ       | 来場者の端末で結果を開く | `/result/{colorId}`              |

iPadの画面ミラーリングは使用しない。各端末がそれぞれのURLを開き、同じ展示状態を共有する。

展示ディスプレイの番号は、来場者から見た順に1から振る。番号は写真の割り当てと演出のずれ（7.2節）に使う。同じ番号を二台で開かない。

本番のブラウザは、iPadが最新版Safari、展示ディスプレイ、写真用、管理画面がChromeの最新安定版とする。

## 5. 一回の体験フロー

目標所要時間は一人あたり2分以内、うち質問回答は60秒以内とする。

| 状態       | 段階               | iPad                                                       | 展示ディスプレイ                                 | 終了条件                                       |
| ---------- | ------------------ | ---------------------------------------------------------- | ------------------------------------------------ | ---------------------------------------------- |
| `idle`     | 待機               | 歓迎文言と「はじめる」を表示                               | 全色の写真を静かに巡回表示                       | 「はじめる」を押す                             |
| `sequence` | 演出               | シーケンスのコンポーネントを表示                           | 待機写真の上にシーケンスのコンポーネントを重ねる | 再生時間が過ぎると、サーバーが次の段階へ進める |
| `intro`    | 導入               | 進捗バーとニックネームの入力欄を表示                       | 待機表示を継続                                   | ニックネームを入力して「→」を押す             |
| `question` | 質問               | 一問ずつ質問文と、入力方式（6.1節）に応じた入力を表示      | 確定した回答に反応する抽象的な色・形の演出を表示 | 全問に回答する                                 |
| `judging`  | 判定               | 2秒間の判定演出を表示                                      | 全画面を一度暗くし、結果演出に備える             | サーバーが2秒後に`result`へ進める              |
| `result`   | 結果発表・持ち帰り | 色名、色面、短いメッセージ、QRコード、「最初に戻る」を表示 | 結果色と対応写真を一斉に表示                     | 「最初に戻る」または60秒経過で`idle`へ戻る     |

`sequence`は、iPadと展示ディスプレイで演出を再生し、再生時間が過ぎると自動で次の段階へ進む段階である。`src/data/sequences.ts`にはID、どの段階の直前に再生するか（`before`）、再生時間（`durationMs`）だけを定義し、見た目は`src/client/sequences/<id>/`のSvelteコンポーネント（iPad用の`Controller.svelte`と展示ディスプレイ用の`Display.svelte`）で自由に書く。`intro`と`question`のそれぞれについて、その段階へ入る直前に一つまで再生できる。仮データでは「はじめる」の後、`intro`の前に再生する。再生中はiPadに操作手段を置かない。

「持ち帰り」は独立した状態ではなく、`result`画面でQRコードを読み取る行為を指す。

質問中は入力を操作して回答を選び、「次へ」で確定する。確定前の値はiPadの中だけで保持し、サーバーへ送らない。「次へ」を押してからサーバーの新しい状態が届くまで、入力と「次へ」を無効にして二重入力を防ぐ。前の質問へ戻った場合は既存回答を表示し、変更して再確定できる。

## 6. 診断仕様

### 6.1 質問

- 問数は診断定義の質問の数とする（仮データは7問）。
- 各問は次の入力方式（`kind`）のいずれか一つを持つ。

| `kind`     | 入力方式   | 画面                                                               | 回答                                           |
| ---------- | ---------- | ------------------------------------------------------------------ | ---------------------------------------------- |
| `single`   | 単選択     | 2〜8個の選択肢から一つを選ぶ                                       | 選択肢ID                                       |
| `multiple` | 複数選択   | 2〜8個の選択肢から`minSelections`個以上`maxSelections`個以下を選ぶ | 選択肢IDの配列（選択肢の定義順）               |
| `slider`   | スライダー | 左右端に対になる語を置き、その間の位置を選ぶ水平スライダー         | 左端0から右端1までの位置                       |
| `map`      | 2Dマップ   | 上下左右の4辺に語を置いた正方形の平面で、位置を一つ選ぶ            | `{ x, y }`（xは左端0〜右端1、yは上端0〜下端1） |

- 左右や上下の対になる語は「静か―にぎやか」のように、どちらにも優劣を感じさせない組にする。
- スライダーは等間隔に5段階の回答位置を置き、IDを左から`far-left | left | center | right | far-right`に固定する。2Dマップは平面を3×3の区画に分け、区画IDを上の行から順に`top-left | top | top-right | left | center | right | bottom-left | bottom | bottom-right`に固定する。回答位置と区画は配点と補助文を持つ。選択肢IDは質問ごとに英小文字、数字、ハイフンで定義する。画面にはIDや数値を表示しない。単選択と複数選択は選択肢の文言で、スライダーと2Dマップはつまみやピンの位置と短い補助文で、選んだ内容を伝える。補助文は、スライダーではつまみに最も近い回答位置のもの、2Dマップではピンを含む区画のものを表示する。
- 新しい質問を開いた時点では未回答とする。スライダーのつまみと2Dマップのピンは中央へ薄く表示するが、この仮表示を`center`の回答として扱わない。単選択、スライダー、2Dマップは一度操作するまで「次へ」を無効にする。複数選択は選択数が`minSelections`に届くまで「次へ」を無効にし、`maxSelections`に達したら選んでいない選択肢を押せなくする。
- スライダーのつまみと2Dマップのピンはスナップせず、指を離した位置に止まる。iPadは位置を小数第3位に丸めて送る。選んでも自動では次へ進まず、「次へ」を押した時点で選んでいる回答を送る。
- 質問文は一読で答えられる長さとし、性格の優劣を感じさせる表現を避ける。
- 正解・不正解や得点表示は行わない。
- 画面上部に現在の質問番号を `3 / 7` の形式で表示する。
- サーバーは、表示中の質問の入力方式に合わない回答（未定義のID、範囲外の選択数、重複、定義順でない並び）を拒否する。質問定義を変えてデプロイした後は、変更前に保存した回答のうち定義に合わないものを除く。最終問に回答した時点で未回答の質問が残っていれば、判定せずにその質問へ戻す。

質問テーマは「今選びたいもの」に統一する。季節、時間帯、場所、光、音、手触り、過ごし方の7テーマを基本案とし、心理診断のような断定を避ける。

### 6.2 結果色

MVPは8結果とする。色名、基準色、背景色、文字色、説明文、代表画像を一つの結果定義として管理する。

| ID      | 表示名（仮）       | 基準色（仮） | 写真の方向性           |
| ------- | ------------------ | ------------ | ---------------------- |
| red     | ルビーレッド       | `#C9364F`    | 熱、生命、近距離の質感 |
| orange  | コーラルオレンジ   | `#F0784B`    | 夕方、親密さ、温度     |
| yellow  | サンイエロー       | `#E5B83B`    | 光、開放感、軽さ       |
| green   | エメラルドグリーン | `#2F9B78`    | 植物、水、静かな成長   |
| cyan    | アクアブルー       | `#39A8B8`    | 透明感、風、反射       |
| blue    | コバルトブルー     | `#315AA9`    | 夜、奥行き、集中       |
| violet  | アメジスト         | `#7653A6`    | 影、余韻、非日常       |
| magenta | マゼンタピンク     | `#B94083`    | 華やかさ、遊び、躍動   |

基準色は画面間の演出に用いる代表値であり、展示写真を着色するための値ではない。背景色（`backgroundColor`）と文字色（`foregroundColor`）は基準色から実行時に作らず、定義に持たせる。両者のコントラスト比は4.5:1以上とする。

### 6.3 判定方法

- 各問の選択肢、回答位置、区画は、8色のうち1〜2色に加点する固定スコアを持つ。同じ回答位置や区画でも質問ごとに配点を定義する。
- 複数選択では、選んだ選択肢の配点を合計する。選択数でその問の重みが変わるため、選択肢の点数と`maxSelections`で他の問との釣り合いをとる。
- スライダーでは、両隣の回答位置の配点を距離で混ぜる。例えば`far-left`と`left`のちょうど中間なら、両方の配点を半分ずつ加える。
- 2Dマップでは、選んだ位置を囲む4区画の中心の配点を、横と縦それぞれの距離で混ぜる（双線形補間）。横または縦の位置が外周の区画の中心より外側にあるときは、その向きの位置を外周の区画の中心とみなす。このため、辺の近くでは外周の2区画を距離で混ぜ、四隅の近くではその隅の区画の配点だけを使う。区画の中心ではその区画の配点だけを加える。
- スライダーと2Dマップの得点は小数になる。得点の比較では、差が10億分の1以下なら同点とみなす。
- 全回答の合計点が最も高い色を結果とする。
- 同点時は、後半3問で得点が高い色を優先する。
- それでも同点の場合は、色定義に設定した固定優先順位で決定する。
- 同じ回答列からは常に同じ結果を返し、ランダム判定は行わない。

質問文、入力方式、選択肢や端・辺の語、補助文、配点はコードへ直接埋め込まず、一つの診断定義データとして管理する。公開前に回答パターンを集計し（`pnpm distribution`）、一度も出ない色がないこと、および一色へ極端に偏っていないことを確認する。スライダーと2Dマップは位置が連続値のため、スライダーを等しい幅の8区間に、2Dマップを縦横それぞれ等しい幅の9×9区間に分け、各区間の中点で数える。端を含む等間隔の点で数えると、端の点が表す範囲は他より狭い（端では半分、2Dマップの隅では4分の1）のに同じ1通りとして数えるため、割合がずれる。集計するパターン数は各問の候補の数の積で、仮データでは27,869,184通りとなる。

## 7. 画面仕様

### 7.1 iPad操作画面

- 縦向きを基本とし、横向きでも操作不能にならないレイアウトにする。
- 一画面に一つの主操作だけを置く。
- スライダーのトラックは横幅280px以上、つまみのタップ領域は44 × 44 CSS px以上とし、トラック上の任意の位置のタップとつまみのドラッグの両方で、指の位置を選べるようにする。読み上げとキーボード操作のために、5段階の回答位置を見えないラジオボタンとしても置き、矢印キーで別の回答位置へ移るとつまみがその回答位置へ動くようにする。
- トラック上に5個の等間隔な目盛りを常時表示し、現在位置の目盛りとつまみを拡大する。選択中の補助文をトラック直下へ表示する。
- 2Dマップの平面は一辺220px以上の正方形とし、平面上の任意の位置のタップとピンのドラッグの両方で、指の位置を選べるようにする。9区画の中心に印を常時表示し、ピンを含む区画の印を拡大する。その区画の補助文を平面の下へ表示する。読み上げとキーボード操作のために、9区画を見えないラジオボタンとしても置き、矢印キーで別の区画へ移るとピンがその区画の中心へ動くようにする。
- 単選択と複数選択の選択肢は高さ64px以上のボタンとし、単選択は丸、複数選択は四角の印を左に置く。選んだ選択肢は塗りつぶし、印に単選択は点、複数選択はチェックを入れる。
- 未回答、操作中、確定待ち、確定済み、無効の状態を、つまみ・ピン・選択肢の形、枠、ラベルで見分けられるようにする。色だけで状態を区別しない。
- 結果画面には色名、色面、50文字以内のメッセージ、QRコードと結果URL（10.3節）、「最初に戻る」を表示する。
- 通信が切れている間は「再接続しています」を全面に表示して操作を止める。再接続したらサーバーの状態をそのまま表示する。ブラウザを再読み込みしても、進行中の診断や結果へ戻る。

### 7.2 展示ディスプレイ

#### 7.2.1 画面番号

展示ディスプレイは`/display/{番号}`を開く。番号から1を引いた値を`displayOrder`とし、写真の割り当てと演出のずれに使う。台数を事前に登録する一覧は持たない。

#### 7.2.2 共通レイアウト

- 写真を作品として見せるため、一画面につき一作品だけを表示する。
- 画面全体を背景面とし、上下左右に`clamp(32px, 5vmin, 96px)`の余白を取った領域へ写真を配置する。
- 写真は`object-fit: contain`、中央揃えで表示する。クロップ、変形、色フィルターを行わない。
- 待機状態の背景は`#0B0B0B`とする。結果状態では結果色定義の`backgroundColor`を使う。
- 色名などの文字には結果色定義の`foregroundColor`を使う。

演出の見た目は `docs/visual-language.md` に従う。

#### 7.2.3 待機表示

待機用写真は、写真定義で`idleEnabled: true`のものを`idleOrder`昇順、同値の場合は写真ID昇順で並べた共通プレイリストとする。

- 一作品の表示枠は8秒とし、先頭1秒で前作品からクロスフェードする。`prefers-reduced-motion: reduce`ではクロスフェードを行わない。
- 拡大縮小、パン、ランダムな並べ替えは行わない。
- 枠の番号は、補正済みサーバー時刻と待機の開始時刻から求める。再接続した画面も同じ枠から再開する。
- 写真数を`P`とし、`displayOrder < P`の画面はプレイリストの`(枠の番号 + displayOrder) mod P`番目を表示する。同時刻に同じ写真を複数画面へ表示しない。
- `displayOrder >= P`の画面は展示タイトルを表示する。

#### 7.2.4 結果表示と割り当て

結果色に紐づく写真は`resultOrder`昇順、同値の場合は写真ID昇順で並べる。写真数を`P`としたとき、`displayOrder < P`の画面には同じ番号の写真を割り当てる。`displayOrder >= P`の画面には写真を複製せず、結果色の`backgroundColor`を全面に表示し、その中央へ`foregroundColor`で色名を表示する。

結果の切り替え時刻は`judging`の`phaseEndsAt`とし、各画面が補正済みサーバー時刻でその時刻を待って切り替える。`result`開始後に接続した画面は結果演出を再生せず、完了状態をすぐに表示する。

#### 7.2.5 写真の読み込み

- 各画面は、8色それぞれで自分に割り当てられる結果写真を接続後に読み込んでおく。
- 結果開始時刻は写真の読み込みを待たない。開始時刻までに読み込めなかった画面は、そのセッションの間7.2.4節の色名表示にする。
- 一画面の読み込み失敗によって、ほかの画面の表示や診断の進行を止めない。

### 7.3 写真用

写真用の画面は`/photo/{番号}`を開き、診断の状態とは関係なく、待機用プレイリストを8秒ごとに巡回表示する。番号ごとに開始位置を一作品ずつずらす。管理画面の端末一覧に表示するため、サーバーへは接続する。

### 7.4 管理画面

管理画面は`/admin`を開く。次を提供する。

- 現在の段階、結果色、セッションID。回答内容は表示しない。
- 診断受付の停止と再開。停止は新規開始だけを拒否し、進行中の診断は最後まで続ける。
- 全端末を待機状態へ戻す強制リセット。
- 各結果色の表示確認（待機中だけ）。
- 接続中の端末一覧と最終受信時刻。接続が切れたまま最後の受信から15秒を過ぎた端末は「切断」と表示する。タブを閉じるなどで接続を正常に閉じた端末は一覧から消える。

## 8. 同期と状態管理

展示全体で一つのDurable Objectが、次の展示状態を保存して全端末へ配信する。

```text
sessionId: string | null
phase: idle | sequence | intro | question | judging | result
nickname: string | null
sequenceId: string | null
questionIndex: number | null
answers: Record<QuestionId, Answer>  // 単選択の選択肢ID、複数選択の選択肢IDの配列、スライダーの位置（0〜1）、2Dマップの位置 { x, y }
resultColorId: ColorId | null
previewColorId: ColorId | null
phaseStartedAt: number
phaseEndsAt: number | null
revision: number
accepting: boolean
```

時刻はサーバー時刻のUnix time milliseconds、`questionIndex`は0始まりとする。`nickname`は`intro`で入力したニックネームで、`idle`へ戻るまで保持する。`revision`は状態が変わるたびに1増える番号で、展示ディスプレイは「一問確定した」という合図として使う。

### 8.1 初期値

Durable Objectを初めて作成したときは、`phase`を`idle`、`accepting`を`true`、`revision`を0、`phaseStartedAt`を作成時刻とし、それ以外を空（`null`または`{}`）にする。

`idle`から開始するときに`crypto.randomUUID()`で新しい`sessionId`を発行し、`idle`へ戻るときに`null`へ戻す。

### 8.2 状態遷移と期限

| 現在の状態              | 契機                         | 次の状態                          | 同時に行う処理                                                                                                 |
| ----------------------- | ---------------------------- | --------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `idle`                  | iPadの開始操作               | `sequence`または`intro`           | 新しい`sessionId`を発行する。`intro`の前のシーケンスがあれば`sequence`へ入る                                   |
| `intro`                 | iPadのニックネーム送信       | `sequence`または`question`        | ニックネームを保存する。`question`の前のシーケンスがあれば`sequence`へ入り、なければ`questionIndex`を0にする   |
| `sequence`              | 再生時間が経過               | `intro`、`question`、または`idle` | シーケンスの`before`の段階へ入る（`question`なら`questionIndex`を0にする）。定義が見つからなければ`idle`へ戻す |
| `question`              | 最終問以外の回答             | `question`                        | 回答を保存し、`questionIndex`を1進める                                                                         |
| `question`              | 「戻る」                     | `question`                        | `questionIndex`を1戻し、既存回答は保持する                                                                     |
| `question`              | 最終問の回答                 | `judging`                         | 結果を確定して`resultColorId`を設定し、`answers`を消去する                                                     |
| `judging`               | 2秒経過                      | `result`                          | 60秒後を`phaseEndsAt`にする                                                                                    |
| `result`                | 「最初に戻る」または60秒経過 | `idle`                            | セッション状態を初期化する                                                                                     |
| `intro`または`question` | 最終操作から5分経過          | `idle`                            | 放置された回答とセッションを消去する                                                                           |
| 任意                    | 管理画面の強制リセット       | `idle`                            | 現在の処理を中止してセッション状態を初期化する                                                                 |

`phaseEndsAt`は`sequence`では再生時間後、`judging`では2秒後、`result`では60秒後、`intro`と`question`では最後のiPad操作から5分後、`idle`では`null`とする。期限はDurable Objectのalarmで処理する。alarmが遅れた場合も、次の接続や操作の前に期限を確認し、期限切れの状態を配信しない。

`idle`へ戻すときは`accepting`以外のセッション状態を初期値へ戻す。`accepting`が`false`の間、iPadは待機画面の代わりに受付停止を表示し、新しい診断を開始できない。

現在の状態で実行できない操作は拒否し、状態を変えない。そのため、同じ操作が二度届いても二度目は拒否される（例: 表示中ではない質問への回答、`idle`以外での開始）。強制リセットの後に古いiPad操作が届いても、診断は復帰しない。

### 8.3 通信

各端末は同一オリジンの`/api/realtime?role={役割}&screen={番号}`へWebSocketで接続する。役割は`controller`、`display`、`photo`、`admin`のいずれかで、`screen`は展示ディスプレイと写真用だけに付ける。メッセージはJSONテキストとする。

| 方向                     | `type`    | 内容                           |
| ------------------------ | --------- | ------------------------------ |
| クライアントからサーバー | `command` | 状態を変える操作               |
| クライアントからサーバー | `ping`    | 5秒ごとの生存確認と時刻計測    |
| サーバーからクライアント | `state`   | 役割別の現在状態とサーバー時刻 |
| サーバーからクライアント | `pong`    | `ping`の送信時刻とサーバー時刻 |

- 接続するとすぐ、サーバーが現在状態を`state`で送る。
- 状態が変わると、サーバーは送信元を含む全端末へ`state`を送る。操作を拒否したときは、送信元にだけ現在状態を送る。iPadと管理画面は、`state`が届いた時点で確定待ちの表示を解除する。
- 再送はしない。通信が切れたら、端末は待ち時間を0.5秒から10秒まで倍にしながら接続し直し、接続後に届く状態を正とする。
- 15秒間`pong`が届かない場合も、切断として接続し直す。
- 診断用iPadは複数台つないでも、どれからでも操作できる。運用では一台だけを置く。

役割ごとに送る状態と使える操作は次のとおりとする。

| 役割         | 受け取る状態                                      | 使える操作                                                   |
| ------------ | ------------------------------------------------- | ------------------------------------------------------------ |
| `controller` | 全項目                                            | `start`、`continue`、`answer`、`back`、`returnToIdle`        |
| `display`    | `answers`、`questionIndex`、`accepting`を除く項目 | なし                                                         |
| `photo`      | `display`と同じ                                   | なし                                                         |
| `admin`      | `answers`を除く項目と、接続中の端末一覧           | `setAccepting`、`forceReset`、`previewColor`、`clearPreview` |

`previewColor`は`idle`でのみ受理し、展示ディスプレイに確認用の色を表示する。`clearPreview`、`start`、`forceReset`で解除する。

### 8.4 時刻補正

端末は`ping`の往復から「サーバー時刻 - 端末時刻」を求め、直近6回（30秒分）のうち往復時間が最も短い計測の値を使う。展示ディスプレイの演出と結果の切り替えは、この補正済みサーバー時刻で決める。

### 9.2 アプリケーション構成

一つのSvelteアプリで、起動時の`location.pathname`から表示する画面を決める（4章の表）。診断定義、結果色、メッセージ、状態遷移は`src/shared/`の共通モジュールに置く。Workerは`/result/*`の公開判定（10.1節）と`/api/realtime`を処理し、それ以外は静的ファイルとSPAの`index.html`を返す。

### 9.3 検証

- Vitestで回答パターンの集計、同点処理、状態遷移、二重操作、メッセージ検証、役割別の配信を確認する。
- Playwrightで展示ディスプレイを1台と3台開いた構成を実行し、開始、回答、写真割り当て、結果の切り替え、再接続、強制リセットを確認する。
- `pnpm check`、テスト、production buildがすべて成功した状態をデプロイ可能とする。

照明連携の技術は機材決定後に9.1節へ追記する。Webアプリからは結果色IDと開始時刻だけを渡す境界を保ち、機材固有の処理を診断ロジックへ含めない。

## 10. 結果の受け渡し

MVPはデジタル受け渡しとする。結果画面に結果色ごとのQRコードを表示し、読み取るとその色の結果ページを来場者自身の端末で開く。

### 10.1 公開URLと公開期間

カスタムドメインは取得せず、Cloudflareが発行する`https://dpc-school-festival.<subdomain>.workers.dev`を公開元とする。初回デプロイ後に、確定したURLを末尾スラッシュなしで`wrangler.jsonc`の`PUBLIC_ORIGIN`へ設定する。QRコードと結果URLは必ずこの値から作る。`PUBLIC_ORIGIN`がHTTPSでない場合、または`https://dpc-school-festival.<subdomain>.workers.dev`の形（末尾スラッシュなし）でない場合はproduction buildを失敗させる。

公開終了日時はISO 8601形式のUTC時刻で`RESULTS_PUBLISHED_UNTIL`へ設定する。終了日時より前は結果ページをHTTP 200で返し、以降は`/result/*`をHTTP 410で返す。410ページには展示名と「この展示の結果ページは公開を終了しました」だけを表示する。存在しない`colorId`はHTTP 404とする。

### 10.2 結果ページの内容

結果ページには次だけを含める。

- 色名と色面
- 診断メッセージ
- 展示写真のうち配布許可済みの代表画像と、その作者クレジット（`© {creditName}`）
- 展示名と開催情報

各結果色の`representativePhotoId`は、同じ`resultColorId`を持ち、`shareAllowed: true`で`creditName`のある写真を指す。条件を満たさない場合はproduction buildを失敗させる。画像を読み込めない場合は、画像とクレジットを隠して色面と診断メッセージを表示する。

### 10.3 QRコード

QRコードへ格納する文字列は`${PUBLIC_ORIGIN}/result/${colorId}`だけとし、セッションIDや回答内容を含めない。同じ色になった来場者は同じ結果ページを開く。結果はサーバーへ保存しない。

- iPad上でSVGとして生成し、外部のQR生成APIへURLを送らない。表示サイズは256 × 256 CSS px、前景`#000000`、背景`#FFFFFF`、Quiet Zoneは4 modules、誤り訂正レベルはMとする。
- QRコードの直下に、同じ結果URLをテキストで表示する。
- 生成に失敗した場合は、QRコードの代わりに「QRコードを表示できませんでした」と結果URLを表示する。結果表示と60秒のタイマーは止めない。

公開前に8色すべてのQRコードを本番のiPadへ表示し、iPhoneとAndroidの標準カメラで読み取れることを会場の照明で確認する。

## 11. 照明・装飾連携

照明連携はWeb画面と切り離した出力先として扱い、結果色IDを受けて事前登録した照明シーンを再生する。

- RGB値をそのまま照明へ送らず、会場で調整した8個の照明シーンを用いる。
- 通信失敗時も画面上の診断を完了させる。
- 強制リセット時は待機用の白色または中立色へ戻す。
- 強い高速点滅は使わない。

採用機材と制御方式が決まるまでは、照明連携を必須の完了条件に含めない。

## 12. 写真素材の要件

### 12.1 表示用ファイル

- 原本は表示用ファイルと分けて保管し、Webアプリから直接配信しない。
- 写真IDは小文字ASCII英数字をハイフンで区切った形式（`^[a-z0-9]+(?:-[a-z0-9]+)*$`）とする。
- 一つの写真IDから`public/photos/{photoId}.avif`と`public/photos/{photoId}.jpg`の二ファイルを`pnpm export-photos`で書き出す。AVIFを優先し、読み込めないブラウザにはJPEGを表示する。
- 両形式は同じ原本から生成した、回転情報を反映したsRGB画像とする。
- 長辺は3,840px以下とし、原本より大きくしない。一ファイルの上限はAVIF 2MiB、JPEG 3MiBとする。欠落、上限超過、二形式の寸法の不一致はproduction buildを失敗させる。

### 12.2 メタデータと画面割り当て

- 各結果色につき、展示ディスプレイの台数以上を目安に用意する。足りない画面は色名表示になる（7.2.4節）。
- 色だけで分類せず、結果メッセージと写真のテーマが一致するものを選ぶ。
- 各写真に一意の写真ID、`resultColorId`、`resultOrder`、`idleEnabled`、`idleOrder`、`shareAllowed`、`creditName`、任意の`creditUrl`を設定する。
- 写真定義には画面番号を持たせない。画面への割り当ては`displayOrder`と`resultOrder`・`idleOrder`だけで決める。
- 写真IDの重複、ファイルの欠落、未定義の`resultColorId`はproduction buildを失敗させる。
- 展示用データへ文字やUIを焼き込まない。

### 12.3 色の実機確認

会場の照明の下で、全展示ディスプレイと本番のiPadに8色の色面、代表画像、結果写真を表示し（管理画面の表示確認を使う）、写真担当と企画担当の二名が、白飛び・黒つぶれ、意図しない色かぶり、隣の結果色と区別できない状態がないことを確認する。自動輝度、Night Shift、True Toneは切る。

## 13. プライバシーとアクセシビリティ

- 個人を特定できる情報を入力させない。`intro`で入力するのは来場者が自由に決めるニックネームで、本名を求めない。
- ニックネームは`src/shared/nickname.ts`で正規化する（NFC正規化、制御文字と書式文字の除去、空白の圧縮、前後の空白の除去）。空、または12文字を超える場合は受け付けない。保存は`intro`の送信から`idle`へ戻るまでとする。ニックネームは診断用iPadにだけ配信し、展示ディスプレイ、写真用、管理画面には配信しない。
- 回答は、再読み込みからの復帰のために`intro`と`question`の間だけDurable Objectへ保存する。最終回答を受理するとき、同じ状態更新で`answers`を消去する。放置された回答は5分後の自動リセットで、強制リセットでは即時に消去する。
- 回答履歴やアクセスログを作らず、Workerのログにも回答を出力しない。
- 操作UIは色覚だけに依存しない。`prefers-reduced-motion: reduce`では大きな動きを抑える。
- 音声は体験成立の必須要素にしない。

## 14. 当日運用

### Cloudflare Access の設定（デプロイ時に一度）

アプリには認証がないため、Cloudflare Access で来場者を締め出す。

1. Workers の設定で、このWorkerの`workers.dev`ルートに Cloudflare Access を有効にする。許可するのはスタッフのメールアドレスだけにする。
2. 来場者が開くパスには、Zero Trust の Access アプリケーションを別に作り、ポリシーを「Bypass / Everyone」にする。対象のパスは`/result`、`/assets`、`/photos`、`/fonts`とする。
3. セッションの有効期間は、当日の開場から閉場までより長くする（例: 24時間）。
4. 各端末（iPad、展示ディスプレイ、写真用、管理画面）は、開場前にスタッフのメールアドレスでログインしておく。

`wrangler.jsonc`ではバージョンごとのプレビューURLを無効にしている。Access の外から入れる入口を増やさないためである。

### 開場前

1. 全端末を同一ネットワークへ接続し、4章のURLを開く。展示ディスプレイは来場者から見た順に番号を振る。
2. 管理画面で、iPad、全展示ディスプレイ、全写真用が「接続中」であることを確認する。
3. 管理画面の表示確認で8色を表示し、画面と照明の対応を確認する。
4. Accessにログインしていないスマートフォンで、結果ページ（例: `/result/red`）が開けること、`/`と`/admin`がAccessのログイン画面になることを確認する。
5. 一回の通し診断を行い、「最初に戻る」で全画面が待機へ戻れば開場可能とする。

### 障害時

- 一画面だけおかしい場合は、そのブラウザを再読み込みする。
- 全画面が同期しない場合は、受付を停止し、管理画面から強制リセットする。
- QRコードだけが表示されない場合は、iPadに出る結果URLで案内を続ける。
- 照明だけが失敗した場合は、照明連携を止めて画面展示を続ける。

## 15. 受け入れ条件

自動テストで確認するもの:

- 集計したすべての回答パターンで、定義済み8色のいずれか一つが返る。スライダーの得点は両隣の回答位置の配点を、2Dマップの得点は位置を囲む区画の中心の配点を、距離で混ぜた値になる。
- 各質問を初めて開いたときは「次へ」が無効で、スライダーはトラックのタップで5段階の回答位置すべてを、2Dマップは平面のタップで9区画すべての中心を選べ、単選択はどの選択肢も選べる。スライダーでは回答位置の間、2Dマップでは区画の中心の間をタップしてもスナップせず、その位置に止まる。複数選択は選択数が下限に届くまで「次へ」が無効で、上限に達すると選んでいない選択肢を押せない。入力の操作だけでは`revision`が増えず、「次へ」で一度だけ回答が受理される。
- 戻る操作で直前の回答が復元され、変更して再確定すると変更後の回答だけが判定へ反映される。
- 入力方式に合わない回答は受理されない。
- 最終回答が二度届いても、結果は一つだけ生成される。
- 展示ディスプレイ1台と3台の両方で、全画面が同じ結果色へ切り替わり、同じ写真が複数の画面へ割り当てられない。
- 結果表示中に再読み込みした展示ディスプレイは、結果演出を再生せず完了状態を表示する。
- 待機写真は8秒ごとに進み、通常設定では先頭1秒だけクロスフェードする。
- 結果写真を読み込めない画面は、開始時刻を遅らせずに色名を表示する。
- `.avif`の取得に失敗しても、同じ写真のJPEGを表示する。
- 「最初に戻る」で全端末が待機表示へ戻り、`result`開始から60秒後には操作がなくても待機表示へ戻る。
- 強制リセット後、回答、結果、QRコードが次の来場者へ残らない。強制リセットの後に届いたiPad操作で診断が復帰しない。
- `intro`または`question`で5分間操作しない場合、`idle`へ戻って回答を消去する。
- 最終回答の受理直後、保存した状態の`answers`が空になる。
- 展示ディスプレイ、写真用、管理画面には回答内容とニックネームが届かない。
- 通信が切れたiPadは操作できず、復旧後はサーバーの状態を表示する。
- 切断した展示ディスプレイは管理画面で「切断」になり、再接続すると「接続中」へ戻る。
- 未定義の`colorId`はHTTP 404、`RESULTS_PUBLISHED_UNTIL`以降はHTTP 410になる。
- 各結果色の代表画像が同色かつ配布可能な写真を指し、結果ページに画像と作者クレジットが表示される。

会場で確認するもの:

- 14章「開場前」の手順をすべて満たす。
- 8色すべてのQRコードを、iPhoneとAndroidの標準カメラで読み取れる。
- 12.3節の色の確認を、写真担当と企画担当の両名が承認する。
- 本番のiPadで`intro`、最長文の`question`、`judging`、`result`を縦向きと横向きで表示し、横スクロールや要素の重なりがなく、主操作に届く。
