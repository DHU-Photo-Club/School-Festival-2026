# あなた色写真展 - 診断インタラクティブ展示 - 仕様書

## 1. 文書の位置づけ

本書は、学園祭で実施するあなた色診断展示の企画・制作・当日運用における基準とする。
未確定事項は末尾の「要決定事項」に集約し、それ以外はMVPの暫定仕様として実装を進める。

## 2. 体験の目的

来場者が直感的な質問に答えると、その回答から一つの「今の自分を表す色」が決まり、写真・画面・教室内の光が同じ色へ変化する体験を提供する。
この診断は、展示作品として楽しむためのものとする。「似合う色」の断定ではなく、「回答から選ばれたあなたの色」と表現する。

### 体験完了の条件

- 来場者が説明を受けなくても、開始から結果表示まで一人で操作できる。
- 結果の色、色名、短いメッセージが同時に表示される。
- 結果表示に合わせて、すべての展示ディスプレイが同じ結果セッションへ切り替わる。
- 次の来場者が前の回答を見ずに、新しい診断を開始できる。

## 3. MVPの範囲

### 実施するもの

- iPad上での診断操作
- 選択回答に基づく結果色の決定
- 複数ディスプレイへの同期表示
- 結果色に対応する写真作品の表示
- 結果画面からのデジタル結果受け渡し
- スタッフによる強制リセットと再接続状態の確認

### MVPでは実施しないもの

- 氏名、年齢、連絡先などの個人情報収集
- カメラや顔画像を用いた自動診断
- 来場者自身による写真投稿
- AIによる診断文や画像のリアルタイム生成
- フルカラー印刷
- 複数人の同時診断

即時印刷と高度な照明制御は、機材と現地検証の結果を踏まえて追加する。

## 4. 利用者と端末

| 種別             | 役割                     | 操作                                               |
| ---------------- | ------------------------ | -------------------------------------------------- |
| 来場者           | 診断を受ける             | iPadで回答し、結果を受け取る                       |
| 展示ディスプレイ | 写真作品と演出を表示する | 操作なし。受信した状態を全画面表示する             |
| 運営スタッフ     | 当日の進行と復旧を行う   | 管理画面から開始可否、接続状態、リセットを操作する |

iPadの画面ミラーリングは使用しない。iPad、展示ディスプレイ、管理画面はそれぞれ専用のWeb画面を開き、同一の展示セッション状態を共有する。

MVPの本番ブラウザは、iPadを端末で更新可能な最新版Safari、展示ディスプレイと管理画面を端末で更新可能な最新版安定版Chromeに固定する。公開前の実機試験後は開催終了までメジャーバージョンを更新しない。

## 5. 一回の体験フロー

目標所要時間は一人あたり2分以内、うち質問回答は60秒以内とする。

| 状態       | 段階               | iPad                                                       | 展示ディスプレイ                                 | 終了条件                                             |
| ---------- | ------------------ | ---------------------------------------------------------- | ------------------------------------------------ | ---------------------------------------------------- |
| `idle`     | 待機               | タイトルと「診断をはじめる」を表示                         | 全色の写真を静かに巡回表示                       | 開始ボタンを押す                                     |
| `intro`    | 導入               | 所要時間と診断の位置づけを表示                             | 待機演出を継続                                   | 「進む」を押す                                       |
| `question` | 質問               | 一問ずつ両端に対比語を置いたスライダーを表示               | 確定した回答に反応する抽象的な色・形の演出を表示 | 全問に回答する                                       |
| `judging`  | 判定               | 2秒間の判定演出を表示                                      | 全画面を一度暗くし、結果演出に備える             | サーバーが2秒後に`result`へ遷移する                  |
| `result`   | 結果発表・持ち帰り | 色名、色面、短いメッセージ、QRコード、「最初に戻る」を表示 | 結果色と対応写真を一斉に表示                     | 手動終了または60秒経過で、サーバーが`idle`へ遷移する |

「持ち帰り」は独立した状態ではなく、`result`画面でQRコードを読み取る行為を指す。「最初に戻る」を押した場合と`result`開始から60秒が経過した場合は、どちらもサーバーが展示状態を`idle`へ変更し、iPad、全展示ディスプレイ、照明を同時に待機状態へ戻す。

質問中はスライダーを操作して回答位置を選び、「次へ」で確定する。ドラッグ中の値はiPad内の未確定値として表示し、サーバーへ送らない。確定後は`ack`を受け取るまでスライダーと「次へ」を無効にして二重入力を防ぐ。前の質問へ戻った場合は既存回答の位置を表示し、変更して再確定できる。

## 6. 診断仕様

### 6.1 質問

- MVPは全7問とする。
- 各問は対になる二つの短い言葉を左右端へ置き、その間を5段階で選ぶ水平スライダーを一つ持つ。左右の語は「静か―にぎやか」のように、どちらにも優劣を感じさせない組にする。
- 5段階の回答IDは左から`far-left | left | center | right | far-right`に固定する。画面にはIDや数値を表示せず、つまみの位置と現在位置を表す短い補助文で伝える。
- 新しい質問を開いた時点では回答を`null`とし、つまみを中央へ薄く表示する。この仮表示を`center`の回答として扱わず、スライダーを一度操作するまで「次へ」を無効にする。意図しない中央回答を防ぐためである。
- スライダーは5位置へスナップし、位置の間に連続値を持たない。つまみを離しても自動では次へ進まず、「次へ」を押したときの位置を回答として送る。
- 質問文は一読で答えられる長さとし、性格の優劣を感じさせる表現を避ける。
- 正解・不正解や進捗を競わせる得点表示は行わない。
- 画面上部に現在位置を `3 / 7` の形式で表示する。

質問テーマは「今選びたいもの」に統一する。季節、時間帯、場所、光、音、手触り、過ごし方の7テーマを基本案とし、心理診断のような断定を避ける。

### 6.2 結果色

MVPは8結果とする。色名、基準色、背景色、文字色、説明文、写真セットを一つの結果定義として管理する。

| ID      | 表示名（仮）       | 基準色（仮） | 写真の方向性           |
| ------- | ------------------ | ------------ | ---------------------- |
| red     | ルビーレッド       | `#C9364F`    | 熱、生命、近距離の質感 |
| orange  | コーラルオレンジ   | `#F0784B`    | 夕方、親密さ、温度     |
| yellow  | サンイエロー       | `#E5B83B`    | 光、開放感、軽さ       |
| green   | エメラルドグリーン | `#2F9B78`    | 植物、水、静かな成長   |
| cyan    | アクアブルー       | `#39A8B8`    | 透明感、風、反射       |
| blue    | コバルトブルー     | `#315AA9`    | 夜、奥行き、集中       |
| violet  | アメジスト         | `#7653A6`    | 影、余韻、非日常       |
| magenta | マゼンタピンク     | `#B94083`    | 華やかさ、遊び、躍動   |

基準色は画面間の演出同期に用いる代表値であり、展示写真を単純に着色するための値ではない。混色名も一つの結果色として扱い、二つの診断結果を同時に返す仕様にはしない。

### 6.3 判定方法

- 各問の5回答位置は、8色のうち1〜2色に加点する固定スコアを持つ。同じ回答位置でも質問ごとに配点を定義する。
- 全回答の合計点が最も高い色を結果とする。
- 同点時は、後半3問で得点が高い色を優先する。
- それでも同点の場合は、色定義に設定した固定優先順位で決定する。
- 同じ回答列からは常に同じ結果を返し、ランダム判定は行わない。

質問文、左右端の語、5回答位置の補助文、配点はコードへ直接埋め込まず、一つの診断定義データとして管理する。公開前に5の7乗となる78,125通りを集計し、特定の色が一度も出ないこと、および一色へ極端に偏ることがないか確認する。

## 7. 画面仕様

### 7.1 iPad操作画面

- 縦向きを基本とし、横向きでも操作不能にならないレイアウトにする。
- 一画面に一つの主操作だけを置く。
- スライダーのトラックは横幅280px以上、つまみのタップ領域は44 × 44 CSS px以上とし、トラックの任意位置のタップとつまみのドラッグの両方で最寄りの回答位置を選べるようにする。
- トラック上に5個の等間隔な目盛りを常時表示し、現在位置の目盛りとつまみを拡大する。左右端の語はトラックの各端と対応する位置へ置き、選択中の補助文をトラック直下へ表示する。
- スライダーは`input[type="range"]`を基礎に、`min="0"`、`max="4"`、`step="1"`を設定する。MVPの操作と受け入れ試験はiPadのタッチ入力だけを対象とし、キーボード操作と読み上げ対応は対象外とする。
- 未回答、操作中、確定待ち、確定済み、無効の状態を、つまみの形、枠、ラベルで見分けられるようにする。
- 色だけで状態を区別せず、形、枠、ラベルの変化を併用する。
- 結果画面には色名、色面、50文字以内のメッセージ、QRコードまたは10.4節の代替表示、終了操作を表示する。
- ブラウザの更新や一時的な通信切断後は、進行中セッションへ復帰する。結果確定後の再読み込みでも同じ結果を表示する。

### 7.2 展示ディスプレイ

展示ディスプレイの台数に最低要件は設けず、台数を事前に登録する一覧も持たない。実際に設置する台数は、8.4節のペアリングで登録済みの展示ディスプレイ（有効な端末セッションを持つもの）の数とし、すべての表示割り当てと受け入れ確認はこの台数を基準にする。

#### 7.2.1 画面IDと設置順

画面IDはペアリングの成功時にサーバーが振る。運営スタッフは、教室の配置が決まった後、各画面を来場者から見た順にペアリングする。

```text
screenId: display-1、display-2、...、display-N
displayOrder: 0、1、...、N - 1（screenId の番号 - 1）
```

- 管理画面で展示ディスプレイ用のペアリングコードを発行するときは、画面IDを指定しない。
- ペアリング成功時、サーバーはほかの有効な端末セッションが使用していない最小の番号の`screenId`を振る。`screenId`と`displayOrder`は重複しない。
- 端末セッションを失効させると、その番号は空き、次にペアリングした画面が使用する。端末を交換するときは、元の端末を失効させてから新しい端末をペアリングすると、同じ番号が振られる。
- ペアリング成功後、サーバーは端末セッションへ`screenId`を保存し、ブラウザを`/display/[screenId]`へ移動させる。
- URLを直接変更しても画面IDは変わらない。URLと端末セッションの`screenId`が一致しない場合は表示を開始せず、再ペアリングを求める。
- 写真の割り当てには文字列の辞書順ではなく`displayOrder`を使用する。

#### 7.2.2 共通レイアウト

- 写真を作品として見せるため、一画面につき一作品だけを表示する。
- 画面全体を背景面とし、上下左右に`clamp(32px, 5vmin, 96px)`の余白を取った領域へ写真を配置する。
- 写真要素は配置領域の幅と高さを100%とし、`object-fit: contain`、中央揃えで表示する。写真全体を表示し、クロップ、変形、色フィルターを行わない。
- 待機状態の背景は`#0B0B0B`とする。結果状態では結果色定義の`backgroundColor`を使用し、基準色から実行時に生成しない。
- 色名などの文字には結果色定義の`foregroundColor`を使用し、`backgroundColor`とのコントラスト比を4.5:1以上にする。

各結果色の定義には、基準色とは別に`backgroundColor`と`foregroundColor`を必須項目として持たせる。写真自体の色を変えず、余白とタイポグラフィだけを結果色に合わせるために使用する。

#### 7.2.3 待機表示

待機用写真は、写真定義で`idleEnabled: true`のものを`idleOrder`昇順、同値の場合は写真ID昇順で並べた共通プレイリストとする。

- 一作品の表示枠は8秒とし、先頭1秒で前作品からクロスフェードする。
- 拡大縮小、パン、ランダムな並べ替えは行わない。
- `prefers-reduced-motion: reduce`ではクロスフェードを行わず、8秒ごとに即時切り替える。
- `cycleIndex`は`floor((補正済みサーバー時刻 - idle.phaseStartedAt) / 8000)`で求める。
- 写真数を`P`、画面の`displayOrder`を`S`とし、`S < P`の画面はプレイリストの`(cycleIndex + S) mod P`番目を表示する。同時刻に同じ写真を複数画面へ表示しない。
- `P`が画面数より少ない場合、`displayOrder >= P`の画面は待機写真の代わりに展示タイトルを表示する。

待機中に再接続した画面は、現在の`cycleIndex`から表示を再開し、プレイリストの先頭へ戻らない。

#### 7.2.4 結果表示と割り当て

結果色に紐づく写真は`resultOrder`昇順、同値の場合は写真ID昇順で並べる。写真数を`P`としたとき、`displayOrder < P`の画面には同じ番号の写真を割り当てる。`displayOrder >= P`の画面には写真を複製せず、結果色の`backgroundColor`を全面に表示し、その中央へ`foregroundColor`で色名を表示する。`P`が0の場合は全画面をこのタイポグラフィ表示にする。

`judging`中から接続している画面は、共有された結果開始時刻に合わせて結果演出を再生する。`result`開始後に接続または再接続した画面は結果演出を再生せず、割り当てられた写真またはタイポグラフィの完了状態を即時表示する。ほかの画面の演出を巻き戻さない。

#### 7.2.5 先読みと失敗時表示

- 各画面は、8色それぞれで自分に割り当てられる結果写真を接続後に先読みする。写真が割り当てられずタイポグラフィ表示になる色では、画像を読み込まない。
- 待機写真は現在枠と次枠の二作品だけを先読みし、枠が進むごとに次の一作品を追加で読み込む。
- 結果用写真8色分と最初の待機二作品について、成功件数と失敗した写真IDを管理画面へ報告する。この対象の読み込みが完了した画面を`準備完了`と表示する。
- 結果開始時刻は写真の読み込み状態によって延期しない。
- 割り当て写真を結果開始時刻までに読み込めなかった画面は、7.2.4のタイポグラフィ表示へフォールバックする。
- 結果表示中に写真の読み込みが完了しても差し替えず、そのセッション中はタイポグラフィ表示を維持する。次の待機状態で再試行する。
- 一画面の読み込み失敗によって、ほかの画面の表示または診断進行を止めない。

### 7.3 管理画面

管理画面は来場者から見えない端末で開く。認証は設けない（8.4節）。次を提供する。

- iPadと各展示ディスプレイの接続状態、最終受信時刻の一覧。接続判定は8.6節に従う。
- 現在の段階と結果色。8.5節の役割別配信に従い、現在および過去の回答内容は受信・表示しない。
- 全端末を待機状態へ戻す強制リセット。回答との競合時は8.3節の優先規則に従う。
- 診断受付の一時停止と再開。停止は新規開始だけを拒否し、進行中の診断は8.2節のとおり完了まで継続する。
- 各結果色の表示確認
- 照明連携を追加した場合の手動オン・オフ

## 8. 同期と状態管理

一回の診断をセッションとして管理し、次の状態を共有する。

```text
sessionId: string | null
phase: idle | intro | question | judging | result
questionIndex: number | null
answers: Record<QuestionId, SliderStopId>
resultColorId: ColorId | null
previewColorId: ColorId | null
phaseStartedAt: number
phaseEndsAt: number | null
revision: number
accepting: boolean
```

時刻はすべてサーバー時刻のUnix time milliseconds、`questionIndex`は0始まりとする。`answers`のキーには質問ID、値には6.1節で定義した回答IDを格納し、配列順には依存しない。

### 8.1 初期値と採番

Durable Objectを初めて作成したときの状態は次のとおりとする。

```text
sessionId: null
phase: idle
questionIndex: null
answers: {}
resultColorId: null
previewColorId: null
phaseStartedAt: 作成時のサーバー時刻
phaseEndsAt: null
revision: 0
accepting: true
```

- `idle`から`intro`へ遷移するときに`crypto.randomUUID()`で新しい`sessionId`を発行し、結果終了まで変更しない。
- `idle`へ戻るときに`sessionId`を`null`へ戻す。過去のIDを再利用しない。
- `revision`は受理した状態変更ごとに1加算し、リセット後も0へ戻さない。
- 接続、切断、拒否した要求は展示状態を変えないため、`revision`を増やさない。
- すべての状態変更は、保存と全接続端末への配信を一回の処理として行う。

### 8.2 状態遷移と期限

| 現在の状態              | 契機                         | 次の状態   | 同時に行う処理                                                                            |
| ----------------------- | ---------------------------- | ---------- | ----------------------------------------------------------------------------------------- |
| `idle`                  | iPadの開始操作               | `intro`    | 新しい`sessionId`を発行する                                                               |
| `intro`                 | iPadの「進む」               | `question` | `questionIndex`を0にする                                                                  |
| `question`              | 最終問以外の回答             | `question` | 回答を更新し、`questionIndex`を1進める                                                    |
| `question`              | 「戻る」                     | `question` | `questionIndex`を1戻し、既存回答は保持する                                                |
| `question`              | 最終問の回答                 | `judging`  | 結果を確定し、`resultColorId`を設定して`questionIndex`を`null`へ戻し、`answers`を消去する |
| `judging`               | 2秒経過                      | `result`   | 全端末で結果演出を開始し、60秒後を`phaseEndsAt`にする                                     |
| `result`                | 「最初に戻る」または60秒経過 | `idle`     | セッション状態を初期化する                                                                |
| `intro`または`question` | 最終操作から5分経過          | `idle`     | 放置された回答とセッションを消去する                                                      |
| 任意                    | 管理画面の強制リセット       | `idle`     | 現在の処理を中止してセッション状態を初期化する                                            |

`phaseStartedAt`は状態へ入った時刻とする。`phaseEndsAt`は`judging`では2秒後、`result`では60秒後、`intro`と`question`では最後に受理したiPad操作から5分後、`idle`では`null`とする。期限到達時はDurable Objectのalarmが遷移を実行する。alarmの実行が遅れた場合は、次の接続または要求を処理する前にも期限を確認し、期限切れ状態を配信しない。

`idle`へ戻すときは、`questionIndex`、`answers`、`resultColorId`、`previewColorId`、`phaseEndsAt`をそれぞれ初期値へ戻す。`accepting`はスタッフが設定した受付状態なので、セッションのリセットでは変更しない。`accepting`が`false`の間、iPadは待機画面の代わりに受付停止を表示し、新しいセッションを開始できない。進行中に`accepting`を`false`へ変更した場合は現在の診断を中断せず、`idle`へ戻った後から受付停止を適用する。

### 8.3 更新競合

- iPadと管理画面の通常要求は、受信済みの`revision`を`expectedRevision`として送る。
- Durable Objectは要求を一件ずつ処理し、`expectedRevision`が現在値と一致する要求だけを受理する。
- 不一致の要求には最新状態を返し、クライアントは自動再送せず画面を最新状態へ合わせる。
- 管理画面の強制リセットだけは`expectedRevision`に関係なく受理し、`revision`を1増やす。
- 強制リセットより前に受理済みのiPad操作があっても、最後に`idle`へ変更する強制リセットを優先する。強制リセット後に届いた古いiPad操作は`expectedRevision`不一致で拒否する。
- 同じ要求IDを再送した場合は最初の応答を返し、同じ状態変更を二度実行しない。

状態の正本はDurable Objectに置き、各画面は受信状態を表示する。結果発表は配信受信時ではなくサーバーが指定した時刻を基準に開始し、画面間の差を抑える。接続が切れた展示画面は最後の表示を維持し、接続中を示す警告を来場者向け画面には出さない。管理画面には切断を表示する。

### 8.4 認証と端末設定

すべての操作画面と展示ディスプレイは同一オリジンから配信し、WebSocket接続にはHTTPSと同一オリジンのWSSだけを使用する。結果ページは認証不要とし、リアルタイム状態へ接続しない。

#### 管理画面

管理画面はパスフレーズなどの認証を設けない。`/admin`を開いた端末はそのまま操作できる。

1. 管理画面を開くと`POST /api/admin/session`を送る。有効な管理セッションがすでにあればそれを使い続け、なければサーバーは32 byteの乱数から管理セッションを発行して`HttpOnly`、`Secure`、`SameSite=Strict`のCookieとして設定する（ローカルネットワークへのHTTPリクエストは、後述の「iPadと展示ディスプレイ」にある例外に従う）。
2. 管理セッションは管理画面のWebSocket接続を識別するために使い、発行から12時間で失効する。失効した場合、管理画面は再読み込みして新しいセッションで接続する。

#### iPadと展示ディスプレイ

1. 管理画面で、端末種別を「診断用iPad」または「展示ディスプレイ」から選ぶ。展示ディスプレイの`screenId`は7.2.1節のとおりペアリング成功時にサーバーが振る。
2. 管理画面が6桁の数字による一回限りのペアリングコードを発行する。コードは5分後または使用成功時に失効する。
3. 対象端末の初期画面でコードを入力し、`POST /api/pair`へ送信する。
4. 認証成功後、サーバーが端末セッションをCookieとして設定する。属性と有効期間は管理セッションと同じとし、役割と`screenId`はサーバー側のセッションへ保存する。
5. 端末はCookieが保存されたことを`GET /api/session`で確認してから、割り当てられた画面へ移動する。保存されていなければ移動せず、使用済みのコードを再送しない。

例外として、ローカルネットワークのホスト（ループバック、プライベートIPv4、`100.64.0.0/10`、`.local`）へのHTTPリクエストでは、管理セッションと端末セッションのCookieに`Secure`を付けない。`Secure`を付けたままでは、`localhost`以外のHTTPオリジンでブラウザがCookieを保存せず、LAN内のHTTP開発サーバーで端末を登録できないためである。本番はHTTPSで配信するため、常に`Secure`を付ける。

WebSocketのUpgrade要求ではCookieを検証し、未認証または失効済みならUpgradeせずHTTP 401を返す。認証済みでも要求した役割が端末セッションと一致しない場合はHTTP 403を返す。操作用トークンをURL、ローカルストレージ、WebSocketメッセージへ含めない。管理画面では端末セッションの一覧、発行時刻、最終受信時刻、失効操作を提供する。

### 8.5 WebSocketプロトコル

WebSocketではUTF-8のJSONテキストメッセージだけを扱い、バイナリフレームは使用しない。すべてのメッセージに`version: 1`と`type`を含め、不明なフィールドは無視し、必須フィールドの不足や型違いは拒否する。

| 方向                         | `type`          | 用途                             | 応答                   |
| ---------------------------- | --------------- | -------------------------------- | ---------------------- |
| クライアントからサーバー     | `hello`         | 接続開始                         | `welcome`または`error` |
| クライアントからサーバー     | `command`       | 状態変更                         | `ack`または`error`     |
| クライアントからサーバー     | `ping`          | 生存確認と時刻計測               | `pong`                 |
| 展示ディスプレイからサーバー | `resultStarted` | 実表示開始時刻の報告             | `ack`または`error`     |
| 診断用iPadからサーバー       | `diagnostic`    | QRコード生成失敗などの運用通知   | `ack`または`error`     |
| サーバーからクライアント     | `state`         | 他端末による状態変更のpush配信   | 応答不要               |
| サーバーから管理画面         | `alert`         | 端末から受けた運用通知のpush配信 | 応答不要               |

接続後5秒以内に、クライアントは最初のメッセージとして次の`hello`を送る。

```json
{
	"version": 1,
	"type": "hello",
	"clientId": "ブラウザごとに生成したUUID"
}
```

サーバーはCookieから役割と端末設定を取得するため、`hello`に役割、`screenId`、認証情報を含めない。認証とプロトコル確認に成功すると、役割に応じた現在状態を`welcome`で返す。

```json
{
	"version": 1,
	"type": "welcome",
	"serverTime": 1789400000000,
	"state": {}
}
```

状態の配信範囲は次のとおりとする。

| 接続種別         | 受信する状態                                                                                         |
| ---------------- | ---------------------------------------------------------------------------------------------------- |
| 診断用iPad       | 8章の全状態                                                                                          |
| 展示ディスプレイ | `sessionId`、`phase`、`resultColorId`、`previewColorId`、`phaseStartedAt`、`phaseEndsAt`、`revision` |
| 管理画面         | `answers`を除く状態と、接続端末一覧                                                                  |

他端末の操作またはサーバータイマーで状態が変わった場合は、次の形式で`state`を配信する。

```json
{
	"version": 1,
	"type": "state",
	"revision": 13,
	"state": {}
}
```

通常の状態変更要求は次の形式とする。

```json
{
	"version": 1,
	"type": "command",
	"requestId": "要求ごとに生成したUUID",
	"expectedRevision": 12,
	"command": {
		"name": "answer",
		"questionId": "light",
		"stopId": "left"
	}
}
```

`command.name`は次だけを許可する。

| 役割       | コマンド                                                                          |
| ---------- | --------------------------------------------------------------------------------- |
| 診断用iPad | `start`、`continue`、`answer`、`back`、`returnToIdle`                             |
| 管理画面   | `setAccepting`、`forceReset`、`releaseController`、`previewColor`、`clearPreview` |

各コマンドの`command`オブジェクトは次の形とする。

| `name`              | 追加フィールド                               | 受理条件                                                           |
| ------------------- | -------------------------------------------- | ------------------------------------------------------------------ |
| `start`             | なし                                         | `phase`が`idle`かつ`accepting`が`true`                             |
| `continue`          | なし                                         | `phase`が`intro`                                                   |
| `answer`            | `questionId: string`、`stopId: SliderStopId` | `phase`が`question`で、表示中の質問と5回答位置のいずれかに一致する |
| `back`              | なし                                         | `phase`が`question`かつ`questionIndex`が1以上                      |
| `returnToIdle`      | なし                                         | `phase`が`result`                                                  |
| `setAccepting`      | `accepting: boolean`                         | 管理画面からの要求                                                 |
| `forceReset`        | なし                                         | 管理画面からの要求                                                 |
| `releaseController` | なし                                         | 管理画面からの要求                                                 |
| `previewColor`      | `colorId: ColorId`                           | 管理画面からの要求かつ`phase`が`idle`                              |
| `clearPreview`      | なし                                         | 管理画面からの要求かつ`previewColorId`が`null`ではない             |

`previewColor`は`idle`でのみ受理し、`previewColorId`を設定して展示ディスプレイに確認用の色を表示する。`clearPreview`、`start`、`forceReset`では`previewColorId`を`null`へ戻す。

`expectedRevision`は`forceReset`以外の`command`で必須とする。`forceReset`では省略でき、指定されていても現在値との一致を要求しない。コマンド固有フィールドは`command`内に置き、トップレベルへ追加しない。

#### ACKと状態配信

サーバーは各`command`、`resultStarted`、`diagnostic`へ、同じ`requestId`を持つ`ack`または`error`を一つ返す。

```json
{
	"version": 1,
	"type": "ack",
	"requestId": "要求のUUID",
	"revision": 13,
	"state": {}
}
```

`command`への`ack`は状態の検証、永続化、`revision`更新が完了した後に返す。送信元には更新後状態を含む`ack`を返し、それ以外の接続端末には役割別の`state`メッセージを配信する。`resultStarted`と`diagnostic`への`ack`は報告の保存後に返し、現在の`revision`を含めて`state`を省略する。クライアントは`command`の`ack`を受け取るまで次の状態へ進まず、同時に複数の状態変更要求を送らない。

クライアントは`requestId`を`crypto.randomUUID()`で要求ごとに生成し、再送時は同じ値を使用する。サーバーは認証セッションIDと`requestId`の組を冪等性キーとして、`command`、`resultStarted`、`diagnostic`の応答を10分間または最大512件までDurable Objectのストレージへ保存する。同じキーを再受信した場合は保存済みの`ack`または`error`を返し、状態変更、計測値保存、配信を繰り返さない。

送信後3秒以内に応答がない場合、接続中なら同じ要求を最大2回再送する。この3秒は性能の受け入れ値ではなく再送タイマーであり、`WebSocket.send()`直前から対応する`ack`または`error`受信までをクライアントの`performance.now()`で測る。送信後に切断した場合は、再接続して`welcome`を受け取った後に未応答の要求を同じ`requestId`で一度だけ再送する。再送後も応答がなければ操作を停止し、管理画面からの確認を求める。

#### エラー

```json
{
	"version": 1,
	"type": "error",
	"requestId": "要求のUUIDまたはnull",
	"code": "STALE_REVISION",
	"message": "表示状態を更新しました。もう一度操作してください。",
	"retryable": false,
	"state": {}
}
```

| コード              | 条件                               | 処理                                                                                         |
| ------------------- | ---------------------------------- | -------------------------------------------------------------------------------------------- |
| `INVALID_MESSAGE`   | JSON、必須フィールド、型が不正     | 要求を破棄する                                                                               |
| `PROTOCOL_MISMATCH` | `version`が1ではない               | エラー送信後に接続を閉じる                                                                   |
| `UNAUTHENTICATED`   | 接続後にセッションが失効した       | エラー送信後に接続を閉じ、端末はペアリング画面へ戻り、管理画面は新しいセッションで接続し直す |
| `FORBIDDEN`         | 役割に許可されていないコマンド     | 要求を破棄する                                                                               |
| `STALE_REVISION`    | `expectedRevision`が現在値と不一致 | 最新の役割別状態を返す                                                                       |
| `INVALID_PHASE`     | 現在状態では実行できないコマンド   | 最新の役割別状態を返す                                                                       |
| `CONTROLLER_IN_USE` | 別のiPadが操作端末を占有中         | 操作不可画面を表示する                                                                       |
| `NOT_ACCEPTING`     | 受付停止中に`start`した            | 受付停止画面を表示する                                                                       |
| `INTERNAL_ERROR`    | サーバー内部の失敗                 | 状態を変更せず、管理画面に障害を表示する                                                     |

エラー応答では`revision`を増やさない。`message`は利用者向けの固定文言とし、例外メッセージ、スタックトレース、認証情報を含めない。JSONとして解釈できないメッセージ、`hello`の5秒タイムアウト、または連続3回の`INVALID_MESSAGE`では接続を閉じる。

| Close code | 条件                                     |
| ---------- | ---------------------------------------- |
| `4000`     | 不正メッセージが連続3回に達した          |
| `4001`     | 接続中に認証セッションが失効した         |
| `4002`     | プロトコルバージョンが一致しない         |
| `4008`     | 接続から5秒以内に`hello`を受信しなかった |
| `4009`     | 同じiPadの新しい接続へ操作権限を移した   |

### 8.6 接続監視と時刻補正

クライアントは5秒ごとに次の`ping`を送り、サーバーは`pong`を返す。`clientSentAt`には`performance.timeOrigin + performance.now()`を使用する。

```json
{
	"version": 1,
	"type": "ping",
	"pingId": "計測ごとに生成したUUID",
	"clientSentAt": 1789400000000
}
```

```json
{
	"version": 1,
	"type": "pong",
	"pingId": "受信したUUID",
	"clientSentAt": 1789400000000,
	"serverTime": 1789400000030
}
```

サーバーは`hello`、`command`、`ping`、`resultStarted`、`diagnostic`のいずれかを最後に受信した時刻を`lastReceivedAt`として接続ごとに保持する。

- WebSocketのcloseを受信した場合は、その時点で切断扱いにする。
- closeを受信していなくても、最後の有効メッセージから15秒経過した端末は切断扱いにして接続を閉じる。
- 管理画面にはサーバー時刻基準の`lastReceivedAt`と、`接続中`または`切断`を表示する。
- 再接続に成功した端末は新しい`hello`と`welcome`が完了した時点で接続中へ戻す。

接続直後、クライアントは200ms間隔で5回の`ping`を送り、各応答について次を計算する。

```text
roundTripTime = clientReceivedAt - clientSentAt
clockOffset = serverTime - ((clientSentAt + clientReceivedAt) / 2)
```

往復時間が長い2件を除外し、残る3件の`clockOffset`中央値を時刻補正値として使用する。この5回計測を30秒ごとに行う。最小往復時間が400msを超える場合、または採用した3件の補正値の最大差が100msを超える場合は、管理画面に「同期精度低下」を表示する。

### 8.7 結果同期の計測

最終回答を受理したサーバーは、`judging.phaseStartedAt`を現在時刻、`judging.phaseEndsAt`を正確に2,000ms後として保存・配信する。各展示ディスプレイは時刻補正済みの`phaseEndsAt`で、判定用の暗転から結果色または写真へ切り替える。これにより、結果開始時刻は判定開始時点から2,000ms先行して通知される。

同期差は、各展示ディスプレイで判定表示から結果表示へ初めて切り替わった`requestAnimationFrame`の時刻で測る。端末は次の`resultStarted`を送る。

```json
{
	"version": 1,
	"type": "resultStarted",
	"requestId": "報告ごとに生成したUUID",
	"sessionId": "現在のセッションUUID",
	"screenId": "display-1",
	"actualStartedAt": 1789400002008
}
```

`actualStartedAt`は`performance.timeOrigin + performance.now()`へ時刻補正値を加えた値とする。サーバーは認証セッションに結び付いた`screenId`とメッセージ内の値が一致する場合だけ受理する。

同じ`sessionId`について、結果開始前から接続済みだった展示ディスプレイの`actualStartedAt`の最大値と最小値の差を同期差とする。結果開始後に接続した画面と、開始時点で切断扱いだった画面は計測対象から除外する。200ms以内の受け入れ条件は展示ディスプレイ間だけに適用し、iPadと照明は含めない。管理画面には各画面の開始時刻、同期差、計測対象外の理由を表示する。

### 8.8 通信断中のiPad操作

WebSocketが未接続、close済み、または15秒間`pong`を受信できない場合、iPadは再接続中のオーバーレイを表示して回答、戻る、開始、終了の操作を無効にする。通信断中に新しい回答をローカル保存または送信待ちキューへ追加しない。

接続中に「次へ」をタップした場合は100ms以内にpending表示を出すが、回答確定と画面遷移は`ack`受信後に行う。送信済みで応答だけを失った一件は8.5節の規則で同じ`requestId`を使って再送する。再接続時は`welcome`のサーバー状態を正本とし、pending表示と一致しなければpendingを破棄してサーバー状態へ戻す。

## 9. 技術スタック

### 9.1 採用技術

| 区分                 | 採用技術                                               | 採用理由                                                                   |
| -------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------- |
| 言語                 | TypeScript                                             | 画面、通信メッセージ、診断定義で同じ型を共有するため                       |
| UIフレームワーク     | Svelte                                                 | iPad、展示、管理、結果ページを少ない実行時コードで実装するため             |
| ビルド・ローカル開発 | Vite + Cloudflare Vite plugin                          | SvelteのビルドとWorker、Durable Objectのローカル実行を一つの構成で扱うため |
| ホスティング         | Cloudflare Workers Static Assets                       | Web画面、API、静的素材を一つのデプロイで配信するため                       |
| リアルタイム同期     | Cloudflare Durable Objects + WebSocket Hibernation API | 一つの展示状態を複数画面へ双方向配信し、更新順序を一か所で確定するため     |
| 状態保存             | Durable ObjectのSQLiteストレージ                       | 現在状態と短期の認証・通信記録を保持し、別のデータベースを増やさないため   |
| スタイリング         | Svelteコンポーネント内のCSS + CSS Custom Properties    | 展示固有の表現を作りつつ、色や余白の定義を共通化するため                   |
| パッケージ管理       | pnpm                                                   | 依存関係と実行環境をロックファイルで固定するため                           |
| 単体テスト           | Vitest                                                 | 診断判定、状態遷移、メッセージ検証をブラウザなしで確認するため             |
| E2Eテスト            | Playwright                                             | iPad、複数ディスプレイ、管理画面を同時に開く実際のフローを確認するため     |

Node.jsは開発とビルドにのみ使用し、本番実行環境には要求しない。開発開始時点のActive LTSを採用し、バージョンファイルと`packageManager`フィールドで固定する。

サーバーサイドレンダリングを必要としないため、クライアントはSvelteのSPAとして実装する。Cloudflare Workerのエントリポイントはアプリ内で管理し、API要求の処理、静的ファイルの配信、Durable Objectクラスのexportを一つのWorkerにまとめる。

SvelteKit、Tailwind CSS、UIコンポーネントライブラリ、Socket.IO、D1、KV、R2はMVPへ導入しない。標準CSS、標準WebSocket、Durable Objectの組み込みストレージで要件を満たし、依存と運用対象を増やさないためである。写真素材がWorkers Static Assetsの運用に収まらないと実測できた場合に限り、R2への移行を検討する。

### 9.2 アプリケーション構成

一つのSvelteアプリで、URLのパスに応じて次の画面を提供する。ルート数が固定かつ少ないため、ルーティングライブラリは導入せず、起動時に`location.pathname`から表示する最上位コンポーネントを決定する。

| パス                  | 用途                     | 更新権限                                     |
| --------------------- | ------------------------ | -------------------------------------------- |
| `/`                   | iPad診断画面             | 回答と診断進行を更新できる                   |
| `/display/[screenId]` | 展示ディスプレイ         | 状態の受信のみ                               |
| `/admin`              | 運営管理画面             | 受付状態、表示確認、強制リセットを更新できる |
| `/result/[colorId]`   | QRから開く公開結果ページ | リアルタイム状態へ接続しない                 |
| `/api/pair`           | 展示端末のペアリング     | 一回限りのコードを端末セッションへ交換する   |
| `/api/realtime`       | WebSocket接続口          | 端末の役割に応じてメッセージを検証する       |

診断定義、結果色、画面間メッセージ、状態遷移は共通のTypeScriptモジュールに置く。画面ごとに同じ判定ロジックや状態型を複製しない。Workerが`/api/*`を処理し、それ以外の未一致パスにはSPAの`index.html`を返す。

### 9.3 リアルタイム同期

- 展示全体に対して一つのDurable Objectを割り当て、現在の診断セッションと接続端末を管理する。
- Workerの`/api/realtime`はWebSocket要求をDurable Objectへ転送する。
- Durable Objectだけが`revision`を採番し、受理した状態変更を保存して全端末へ配信する。
- 新規接続時は最新の保存状態を直ちに返す。
- `judging`の`phaseEndsAt`を結果演出の開始時刻として事前配信する。各端末は接続時に得たサーバーとの時刻差を補正して開始を予約する。
- WebSocket切断時は指数バックオフで自動再接続し、再接続後は端末側の古い状態ではなくサーバー状態を採用する。
- Workerは8.4節のCookieを検証し、Durable Objectは8.5節の役割別コマンド権限を検証する。

MVPの診断用iPadは一台とする。ブラウザは初回起動時に`clientId`を生成してローカルストレージへ保持し、`hello`で送信する。Durable Objectは認証済み診断端末のうち同時に一つの`clientId`だけへ操作権限を与える。別IDのiPadには`CONTROLLER_IN_USE`を返す。同じIDが再接続した場合は新しい接続へ操作権限を移して古い接続を閉じる。管理画面から操作端末を解放した場合は端末セッションも失効させ、再利用時に新しいペアリングを必要とする。

Durable Objectへ永続化するのは、8章で定義した現在状態、有効な認証・ペアリングセッション、10分以内の冪等性記録だけとする。過去の診断セッション一覧は作成しない。

### 9.4 素材配信

- 診断定義、色定義、結果メッセージ、写真定義はリポジトリ内の静的データとして管理する。展示ディスプレイの台数と並び順は静的データに持たず、7.2.1節のペアリングで決まる。
- 展示写真は12.1節の表示用データを書き出し、Workers Static Assetsから配信する。
- 各写真は`<picture>`要素でAVIFを優先し、AVIFを読み込めないブラウザにはJPEGを表示する。
- QRコードは10.3節に従ってiPad上で生成し、外部のQR生成APIへ結果URLを送信しない。

### 9.5 検証

- Vitestで全回答パターン、同点処理、無効メッセージの拒否、状態遷移、二重確定を検証する。
- Playwrightでは展示ディスプレイを1台と3台ペアリングした二構成を実行し、iPad一画面、管理一画面とともに開始、回答、写真割り当て、結果同期、再接続、強制リセットを検証する。三画面構成は複数クライアント間の重複割り当てと同期を検証する固定テストケースであり、実会場に三台を要求するものではない。
- `svelte-check`、テスト、Cloudflare向けproduction buildがすべて成功した状態をデプロイ可能とする。
- 実会場の合否は自動テストの台数とは切り離し、会場でペアリングした全展示ディスプレイを対象に13.1節と15章の実機試験で判定する。一台でも未接続または未試験なら受け入れ未完了とする。

照明制御の技術は機材決定後に本節へ追記する。Webアプリからは結果色IDと開始時刻だけを渡す境界を維持し、機材固有の処理を診断ロジックへ含めない。

## 10. 結果の受け渡し

MVPはデジタル受け渡しとする。結果画面に結果色ごとのQRコードを表示し、読み取るとその色の結果ページを来場者自身の端末で開く。

### 10.1 公開URLと公開期間

MVPはカスタムドメインを取得せず、Cloudflareが発行する次の`workers.dev` URLを本番公開元として使用する。

```text
https://dpc-school-festival.<Cloudflareアカウントのsubdomain>.workers.dev
```

初回デプロイ後、デプロイ担当者は確定したHTTPS URLを末尾スラッシュなしで`PUBLIC_ORIGIN`へ設定する。QRコード、共有リンク、結果ページ内のURLは、ブラウザで開いているoriginから組み立てず、必ずこの値を正本にする。`PUBLIC_ORIGIN`がHTTPSでない場合、またはデプロイ先と一致しない場合はproduction buildを失敗させる。

公開終了日時はISO 8601形式のUTC時刻で`RESULTS_PUBLISHED_UNTIL`へ設定する。現在時刻が終了日時より前なら結果ページをHTTP 200で返し、終了日時以降は`/result/*`をHTTP 410で返す。410ページには「この展示の結果ページは公開を終了しました」と展示名だけを表示し、色名、診断文、代表画像は表示しない。応答には`Cache-Control: no-store`を付ける。存在しない`colorId`は公開期間内外にかかわらずHTTP 404とする。

`/result/*`はWorkerを必ず先に通し、公開終了判定後にのみSPAを返す。公開終了後も管理・展示画面の運用が必要な場合があるため、Worker全体や`workers.dev`ルートは自動停止しない。

### 10.2 結果ページの内容

結果ページには次だけを含める。

- 色名と色面
- 診断メッセージ
- 展示写真のうち配布許可済みの代表画像
- 展示名と開催情報
- 代表画像の作者クレジット

各結果色の定義に`representativePhotoId`を一つ設定する。指定先は同じ`resultColorId`を持ち、`shareAllowed: true`の写真でなければならない。写真担当責任者が8色それぞれの代表画像を選び、production build前に設定する。8色のいずれかで指定がない、写真が存在しない、または配布不可の場合はproduction buildを失敗させる。

代表画像の直下には`© {creditName}`を常に表示する。`creditUrl`が設定されている場合だけクレジットをリンクにする。`creditName`のない写真は代表画像に指定できない。画像の読み込みに失敗した場合は色面と診断メッセージを表示し、画像枠とクレジットを隠す。

### 10.3 QRコード

結果色IDを`colorId`としたとき、QRコードへ格納する文字列は次の絶対URLだけとする。クエリ文字列、fragment、`sessionId`、回答内容を追加しない。

```text
${PUBLIC_ORIGIN}/result/${encodeURIComponent(colorId)}
```

- 出力形式はSVG、表示サイズは256 × 256 CSS pxとする。
- 前景を`#000000`、背景を`#FFFFFF`とし、結果色による着色、透過、ロゴの重ね合わせを行わない。
- Quiet Zoneは四辺とも4 modules、誤り訂正レベルはMとする。
- QRコードの直下に、同じ結果URLを選択可能なテキストで表示する。
- `PUBLIC_ORIGIN`と`colorId`を検証してから生成し、生成済みSVGをHTML文字列として直接挿入せず、安全なDOMとして描画する。

公開前に8色すべてのQRコードを実機iPadへ表示し、iPhone標準カメラとAndroid標準カメラの両方で確認する。画面から50cm離れた位置で各QRコードを3回読み取り、各回2秒以内に正しいHTTPS URLを認識し、結果ページがHTTP 200で開けば合格とする。会場照明と本番用の画面輝度でこの確認を行う。

### 10.4 QRコード生成失敗

`result`へ入ったときにQRコードを生成し、失敗した場合は500ms後に同じURLで一度だけ再試行する。二回とも失敗した場合はQRコードの領域を隠し、代わりに次を表示する。

```text
QRコードを表示できませんでした
結果URL: {結果色の絶対URL}
```

QRコード生成失敗は診断結果、展示ディスプレイ、照明、60秒の結果タイマーへ影響させず、結果は完了扱いにする。iPadへ技術的なエラー内容を表示せず、管理画面へ`sessionId`、`colorId`、発生時刻を通知する。再試行後に失敗した例外はログへ記録するが、回答内容と認証情報は含めない。

iPadは二回目の失敗後、次の`diagnostic`を送る。

```json
{
	"version": 1,
	"type": "diagnostic",
	"requestId": "報告ごとに生成したUUID",
	"name": "qrGenerationFailed",
	"sessionId": "現在のセッションUUID",
	"colorId": "red",
	"occurredAt": 1789400002500
}
```

サーバーは現在の診断用iPadから、現在の`sessionId`と`resultColorId`に一致する報告だけを受理し、管理画面へ同じ情報を`alert`として配信する。`diagnostic`と`alert`に例外メッセージを含めない。

結果ページは8色の固定URLとし、セッションIDや回答内容を含めない。同じ色になった来場者は同じ結果ページを開く。

共通QRコードだけでは個別結果を識別できないため採用しない。QRコードは結果確定後に該当色のURLから生成し、結果をサーバーへ保存しない。

## 11. 照明・装飾連携

照明連携はWeb画面と切り離した出力先として扱い、結果色IDを受けて事前登録した照明シーンを再生する。

- RGB値をそのまま照明へ送らず、会場で調整した8個の照明シーンを用いる。
- 結果発表の開始時刻に合わせ、0.5〜1.5秒で現在色から結果色へ遷移する。
- 通信失敗時も画面上の診断を完了させ、管理画面だけに失敗を表示する。
- 強制リセット時は待機用の白色または中立色へ戻す。
- 明滅演出を使用する場合は強い高速点滅を避け、事前に安全性を確認する。

採用機材と制御方式が決まるまでは、照明連携を必須の完了条件に含めない。

## 12. 写真素材の要件

### 12.1 表示用ファイル

- 原本は表示用ファイルと分けて保管し、Webアプリから直接配信しない。
- 写真IDは小文字ASCII英数字をハイフンで区切った形式とし、正規表現`^[a-z0-9]+(?:-[a-z0-9]+)*$`に一致させる。一度公開した写真IDはファイルを差し替えても変更しない。
- 一つの写真IDから`public/photos/{photoId}.avif`と`public/photos/{photoId}.jpg`の二ファイルを書き出す。AVIFを第一候補、JPEGをフォールバックとし、PNG、WebP、GIFを展示写真には使用しない。
- 両形式は同じ原本、画角、向き、埋め込みICCプロファイルから生成し、回転情報を画素へ反映したsRGB画像とする。透過は使用しない。
- 長辺は3,840px以下とし、原本より大きくしない。会場で使う展示ディスプレイの最大物理解像度の長辺を超える必要はない。短辺は縦横比を保って決める。
- 一ファイルの上限はAVIF 2MiB、JPEG 3MiBとする。いずれかの形式が欠落する、上限を超える、デコードできない、または二形式の画素寸法が一致しない場合はproduction buildを失敗させる。

### 12.2 メタデータと画面割り当て

- 各結果色につき、`展示ディスプレイ数 + 2` 点以上を目安に用意する。
- 色だけで分類せず、結果メッセージと写真のテーマが一致するものを選ぶ。
- 各写真に一意の写真ID、`resultColorId`、`resultOrder`、`idleEnabled`、`idleOrder`、`shareAllowed`、`creditName`、任意の`creditUrl`を設定する。
- `resultOrder`と`idleOrder`は0始まりの整数とし、同じ値を許可する。同値の場合は写真ID昇順で表示順を確定する。
- 写真定義には`screenId`を持たせない。結果写真は7.2.4節の`displayOrder`と`resultOrder`、待機写真は7.2.3節の`displayOrder`と`idleOrder`だけで画面へ割り当てる。端末交換時も7.2.1節の手順で同じ`screenId`が振られれば、割り当てを維持できるためである。
- production build時に、写真IDの重複、参照先ファイルの欠落、未定義の`resultColorId`を検出した場合は失敗させる。
- 展示用データへ文字やUIを焼き込まない。
- 縦横比が異なる写真は7.2.2の`object-fit: contain`と余白で吸収する。

### 12.3 色の実機確認

色の承認は、原本制作環境だけでなく、会場でペアリングした全展示ディスプレイと本番用iPadで行う。展示ディスプレイは4章で固定したChrome、iPadはSafariを使用し、いずれもproduction buildを全画面表示する。

- 会場を本番時の照明にし、各端末の輝度を80%へ固定する。自動輝度、Night Shift、True Tone、HDR、OSの夜間モードを無効にし、ディスプレイ側で選べる場合は`Standard`または`sRGB`プリセットを使用する。
- 画面ID、OSのカラープロファイル、ブラウザ名とバージョン、物理解像度、輝度設定、ディスプレイの色プリセットを展示ディスプレイごとの検証記録へ残す。
- 8色それぞれについて色面、代表画像、結果写真を表示し、写真担当責任者と企画担当者の二名が、階調の白飛び・黒つぶれ、意図しない色かぶり、隣接する結果色との識別不能がないことを全端末で確認する。両名が全項目を承認した時点で合格とする。
- 一台でも不合格の場合は、その端末だけを例外扱いせず、色定義または表示設定を修正して全端末を再確認する。

## 13. 非機能要件

### 応答と安定性

- iPadの「次へ」タップからpending表示までは100ms以内とする。「次へ」の`pointerup`イベントを受け取った時刻から、pending状態を描画した最初の`requestAnimationFrame`までを`performance.now()`で測り、7問を含む20回の測定で95パーセンタイルが100ms以下、最大値が150ms以下なら合格とする。
- 結果確定から全ディスプレイの演出開始までは3秒以内とする。最終回答の受理時刻として保存した`judging.phaseStartedAt`から、8.7節で受理した対象画面の`actualStartedAt`の最大値までを測り、10セッションすべてで3,000ms以下なら合格とする。
- 展示ディスプレイ間の同期差は8.7節の定義で測り、同じ10セッションすべてで200ms以下なら合格とする。
- 連続100セッションの実行で、再読み込みを必要とする停止が起きないことを確認する。
- 通信を20秒間遮断してから試験端末のネットワークを復旧し、復旧操作を完了した時刻から新しいWebSocketの`welcome`受信までを測る。iPad一台と各展示ディスプレイで3回ずつ実施し、すべて30秒以内に同じサーバー状態へ復帰すれば合格とする。

時間要件の実機試験は、production build、本番Worker、会場LAN、本番用iPad、会場でペアリングした全展示ディスプレイを使い、会場の通常運用と同じ照明・全画面表示で行う。ブラウザの開発者ツール、CPU・通信スロットリング、画面録画を無効にし、写真の初回先読みと8.6節の初回時刻補正が完了してから測定する。測定ログには端末ID、ブラウザ名とバージョン、各開始・終了時刻、算出値、合否を保存する。

### アクセシビリティ

- 本文と操作文字は、想定閲覧距離で読めるサイズにする。
- 操作UIは色覚だけに依存せず、十分な明度差を持たせる。
- 動きが苦手な来場者向けに、iPad側では大きな動きを抑えた表示を使用する。
- 音声は体験成立の必須要素にしない。追加する場合は消音でも情報が欠けないようにする。

### プライバシー

- 個人を特定できる情報を入力させない。
- 回答は進行中セッションの再読み込み復帰に必要なため、`intro`と`question`の間だけDurable Objectへ保存する。
- 最終回答を受理して結果を確定するとき、同じ状態更新で`answers`を消去する。`judging`と`result`では結果色だけを保持する。
- 途中で放置された回答は、最終操作から5分後の自動リセットで消去する。管理画面の強制リセットでも即時に消去する。
- 回答履歴や回答単位のアクセスログを作成せず、Workerのログにも回答メッセージ本文を出力しない。
- 匿名集計はMVPに含めず、追加する場合は集計項目と保存期間を別途定義する。

## 14. 当日運用

### 開場前

1. 全端末を同一ネットワークへ接続する。
2. 管理画面でiPadと全ディスプレイが接続済みであることを確認する。
3. 8色の表示確認を行い、画面と照明の対応を確認する。
4. QR結果ページを会場の外部回線から開けることを確認する。
5. 一回の通し診断を行い、リセット後に全画面が待機へ戻れば開場可能とする。

### 障害時

- 一画面だけ切断した場合は、該当ブラウザを再読み込みして接続状態を確認する。
- 全画面が同期しない場合は、受付を一時停止し、管理画面から強制リセットする。
- QRコード生成だけが失敗した場合は、10.4節のとおり再試行後に結果URLへ切り替え、診断と展示を継続する。
- 照明だけが失敗した場合は、照明連携を無効化して画面展示を継続する。

## 15. 受け入れ条件

- 7問すべての回答経路で、定義済み8色のいずれか一つが返る。
- 各質問を初めて開いたときは「次へ」が無効で、トラックのタップまたはドラッグによって5位置すべてを選択できる。スライダー操作だけでは`revision`が増えず、「次へ」で一度だけ回答が受理される。
- 戻る操作で直前のスライダー位置が復元され、その位置を変更して再確定すると、変更後の回答だけが判定へ反映される。
- 結果確定操作を連打または再送しても、一セッションにつき結果は一つだけ生成される。
- ペアリングした台数にかかわらず、会場でペアリングした全展示ディスプレイを実機試験へ参加させる。未接続または未試験の展示ディスプレイが一台でもあれば受け入れ未完了とする。
- 13.1節の10セッションすべてで、ペアリングした全展示ディスプレイが同じ結果を200ms以内の差で表示開始し、最終回答の受理から3,000ms以内に表示開始する。
- 実機iPadで20回測定したpending表示までの時間が、95パーセンタイル100ms以下かつ最大150ms以下になる。
- 展示ディスプレイを結果表示中に再読み込みすると、同じ結果表示へ復帰する。
- 結果開始後に再接続した展示ディスプレイは、結果演出を再生せず完了状態を即時表示する。
- 待機写真は8秒ごとに次へ進み、通常設定では先頭1秒だけクロスフェードする。
- 同じ待機枠または結果表示で、同じ写真が複数の展示ディスプレイへ割り当てられない。
- 結果写真を読み込めない画面は開始時刻を遅らせず、対応色のタイポグラフィを表示する。
- 写真は指定余白内へ`object-fit: contain`で表示され、縦横比の変更とクロップが発生しない。
- 全写真IDに同寸法のAVIFとJPEGが存在して容量上限を満たす。Playwrightで`.avif`要求を失敗させた場合、写真要素の`currentSrc`が対応する`.jpg`になり、同じ写真を表示する。
- 12.3節の端末設定で8色と写真を確認し、写真担当責任者と企画担当者の両名が全登録端末を承認する。
- 「最初に戻る」を押すと、iPadと全展示ディスプレイが同じ状態更新で待機表示へ戻る。
- `result`開始から60秒後に操作がなくても、サーバーが`idle`へ遷移して全端末を待機表示へ戻す。
- 強制リセット後、回答、結果、QRコードが次の来場者へ残らない。
- iPad操作と強制リセットを同時に送っても、最終状態は`idle`になり、遅れて届いたiPad操作で診断が復帰しない。
- 二台目のiPadを接続すると操作中の案内が表示され、回答や状態を変更できない。管理画面で解放した後は二台目を操作端末にできる。
- 新規状態の`revision`は0で、受理した各更新により1ずつ増え、拒否した要求と接続状態の変化では増えない。
- セッション開始ごとに異なる`sessionId`が発行され、セッション中は変化せず、`idle`へ戻ると`null`になる。
- 最終回答の受理直後、永続状態の`answers`が空になり、結果色だけで`judging`と`result`を継続できる。
- `intro`または`question`で5分間操作しない場合、サーバーが`idle`へ遷移して回答を消去する。
- 未認証のWebSocket UpgradeはHTTP 401、役割不一致はHTTP 403となり、接続が成立しない。
- 発行から5分を超えたペアリングコードと使用済みコードでは端末セッションを発行できない。
- 各`command`は`ack`または`error`を一つ返し、同じ冪等性キーの再送では同じ応答を返して`revision`を増やさない。
- 有効メッセージが15秒間届かない端末は管理画面で切断表示になり、再接続の`welcome`完了後に接続中へ戻る。
- iPadと各展示ディスプレイで通信復旧試験を3回ずつ行い、復旧操作から30秒以内に毎回`welcome`を受信して同じサーバー状態へ戻る。
- `judging`状態は結果開始時刻の2,000ms前までに全接続済み展示画面へ届き、同期差は最初の結果描画フレームで算出される。
- 通信断中にiPadを操作しても回答はローカル保存されず、再接続後は`welcome`で受信した状態が表示される。
- `PUBLIC_ORIGIN`から生成した8色の結果URLがすべてHTTPSで公開され、未定義の`colorId`はHTTP 404になる。
- `RESULTS_PUBLISHED_UNTIL`以降の結果URLはHTTP 410となり、色名、診断文、代表画像を表示しない。
- 各結果色の`representativePhotoId`が同色かつ配布可能な写真を指し、結果ページに画像と作者クレジットが表示される。
- 8色すべてのQRコードが、会場照明下の50cmの距離からiPhoneとAndroidで各3回、2秒以内に正しい結果URLとして読み取れる。
- QRコード生成を二回失敗させても`result`状態と60秒タイマーは継続し、iPadには結果URL、管理画面には`qrGenerationFailed`が表示される。
- 一台が切断しても、ほかの端末と診断操作は停止しない。
- 実機iPad Safariで`intro`、最長文の`question`、`judging`、`result`を縦向きと横向きの両方で表示し、各状態で横スクロール、要素の重なり、画面外へ到達不能な主操作が発生しない。`question`では両向きで回答を送信でき、`result`ではQRコードまたは代替URLと終了操作へ到達できる。
